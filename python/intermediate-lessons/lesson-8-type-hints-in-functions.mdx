> **Source:** Fluent Python, 2nd Edition — Chapter 8 by Luciano Ramalho

Python has a **gradual type system**: annotations are optional, a checker like Mypy assumes `Any` (compatible with everything) wherever a hint is missing, and — this is the part people trip on — **the Python interpreter never enforces any of it**. Type hints exist purely for static tools (type checkers, IDEs, linters) to catch bugs by reading your source code, without running it.

Every example in this lesson runs with real Python, not a type checker, so you'll see the flip side of that directly: code with "wrong" type hints executes exactly the same as code without them. The hints are for the *tools*, not the runtime.

---

## Gradual typing: optional, unenforced, no speedup

A gradual type system has three defining properties: it's **optional** (untyped code is never flagged by default), it does **not** catch type errors **at runtime**, and it does **not** improve performance — annotations carry no bytecode-level benefit today.

<details>
<summary>🧪 A "wrong" argument still runs</summary>

<PistonRunner
  lang="python"
  interactive={false}
  height="340px"
  code={`def show_count(count: int, word: str) -> str:
    if count == 1:
        return f'1 {word}'
    count_str = str(count) if count else 'no'
    return f'{count_str} {word}s'

print(show_count(2, 'bird'))
print(show_count(1, 'bird'))
print(show_count(0, 'bird'))

# count: int says int — Python never checks that at runtime:
print(show_count('surprise', 'bird'))
`}
/>

</details>

A type checker like Mypy would reject that last call — `'surprise'` is not `int`. Plain Python doesn't care; it just runs the code, and in this case the string happens to be truthy so nothing crashes. That gap — between what the annotation *claims* and what the interpreter *checks* — is the whole reason type checkers exist as a separate tool in your CI pipeline, not a language feature.

## Duck typing vs. nominal typing

Plain Python uses **duck typing**: an object's declared type never matters, only whether the operation you attempt actually works at the moment you attempt it. Annotated Python adds **nominal typing** on top, checked statically: a type checker only cares what a variable is *declared* as, and rejects operations that type doesn't advertise — even if, at runtime, the actual object would have handled it fine.

<details>
<summary>🧪 What a type checker would flag, still runs</summary>

<PistonRunner
  lang="python"
  interactive={false}
  height="420px"
  code={`class Bird:
    pass

class Duck(Bird):
    def quack(self):
        print('Quack!')

def alert(birdie):
    birdie.quack()

def alert_duck(birdie: Duck) -> None:
    birdie.quack()

def alert_bird(birdie: Bird) -> None:
    birdie.quack()

daffy = Duck()
alert(daffy)
alert_duck(daffy)
alert_bird(daffy)

woody = Bird()
try:
    alert_bird(woody)
except AttributeError as e:
    print('Runtime error:', e)
`}
/>

</details>

Mypy flags `alert_bird`'s own body — `Bird` has no `.quack()` — the moment it reads `birds.py`, regardless of how the function is ever called. Calling `alert_bird(daffy)` here works at runtime because `daffy` actually is a `Duck`. But `alert_bird(woody)` blows up with `AttributeError`, exactly the failure Mypy was warning about — just discovered at runtime instead of before you shipped it.

## Any vs. object, and "consistent-with"

`Any` is a wildcard: every type is consistent with `Any`, and `Any` is consistent with every type — a type checker lets *anything* flow through it, in either direction. `object` is completely different: everything is a subtype of `object`, so it accepts every value too, but a checker only lets you use operations that `object` itself defines (which is almost nothing). Also worth knowing: PEP 484 special-cases the numeric tower so `int` is consistent-with `float`, and `float` is consistent-with `complex` — even though none of them actually subclass each other.

## Optional and Union types

`Optional[str]` is shorthand for `Union[str, None]` — the value may be a `str` or it may be `None`. It does **not** make the parameter optional by itself; you still need `= None` in the signature for that. `Union[A, B]` means "either type is acceptable," and is the right tool when a function's return value can genuinely be one of several unrelated types.

<details>
<summary>🧪 Optional default, and a Union return type</summary>

<PistonRunner
  lang="python"
  interactive={false}
  height="380px"
  code={`from typing import Optional, Union

def show_count(count: int, singular: str, plural: Optional[str] = None) -> str:
    if count == 1:
        return f'1 {singular}'
    count_str = str(count) if count else 'no'
    if not plural:
        plural = singular + 's'
    return f'{count_str} {plural}'

print(show_count(2, 'child', 'children'))
print(show_count(2, 'bird'))

def parse_token(token: str) -> Union[str, float]:
    try:
        return float(token)
    except ValueError:
        return token

print(parse_token('3.14'), type(parse_token('3.14')))
print(parse_token('hello'), type(parse_token('hello')))
`}
/>

</details>

Avoid `Union` return types when you can — they push a runtime type check onto every caller. `parse_token` is a reasonable exception: a small expression evaluator that genuinely produces either a number or a leftover token.

## Generic collections

Since Python 3.9, built-in collections accept `[]` directly: `list[str]` means "a list of strings," `dict[str, set[str]]` means "a dict mapping strings to sets of strings." `stuff: list` and `stuff: list[Any]` mean exactly the same thing. Return types should stay **concrete** (`list[str]`, not `Sequence[str]`) — Postel's law: be liberal in parameter types, conservative in what you return.

<details>
<summary>🧪 A tokenizer and a first-letter index</summary>

<PistonRunner
  lang="python"
  interactive={false}
  height="380px"
  code={`def tokenize(text: str) -> list[str]:
    return text.upper().split()

print(tokenize('hello brave new world'))

def first_letter_index(words: list[str]) -> dict[str, set[str]]:
    index: dict[str, set[str]] = {}
    for w in words:
        index.setdefault(w[0], set()).add(w)
    return index

idx = first_letter_index(['cat', 'car', 'dog', 'deer'])
print(sorted(idx['c']))
print(sorted(idx['d']))
`}
/>

</details>

Notice `index: dict[str, set[str]] = {}` — a **local variable** annotation. Without it, a type checker can't tell what the empty `{}` is meant to hold, and will ask you to spell it out. The same "accept the abstract type, return the concrete one" logic applies to `collections.abc.Mapping` vs. `dict`: annotate a *parameter* as `Mapping` so callers can pass a `dict`, a `defaultdict`, or a `UserDict` subclass — `dict` alone would reject a `UserDict`, even though it's the recommended way to build a custom mapping.

## Tuple types

Three distinct uses need three distinct annotations. A tuple as a fixed **record** — `tuple[str, float, str]` for `('Shanghai', 24.28, 'China')`. A record with named fields — just use `typing.NamedTuple`, which is consistent-with the equivalent plain tuple type (so a `NamedTuple` instance works anywhere that plain-tuple type is expected — but not the reverse). A tuple of **unspecified length**, uniform type — `tuple[int, ...]`, the literal `...` token meaning "one or more of the same type."

<details>
<summary>🧪 A record, a NamedTuple record, and a variadic tuple</summary>

<PistonRunner
  lang="python"
  interactive={false}
  height="400px"
  code={`from typing import NamedTuple

def display(lat_lon: tuple[float, float]) -> str:
    lat, lon = lat_lon
    ns = 'N' if lat >= 0 else 'S'
    ew = 'E' if lon >= 0 else 'W'
    return f'{abs(lat):0.1f} {ns}, {abs(lon):0.1f} {ew}'

print(display((35.68, 139.69)))

class Coordinate(NamedTuple):
    lat: float
    lon: float

tokyo = Coordinate(35.68, 139.69)
print(display(tokyo))

def total(nums: tuple[int, ...]) -> int:
    return sum(nums)

print(total((1, 2, 3, 4)))
`}
/>

</details>

`display` is annotated to take a plain `tuple[float, float]`, but a `Coordinate` (a `NamedTuple`) passes through it without complaint from a type checker or the runtime — that's the "consistent-with" relationship in action.

## TypeVar and generic functions

A parameterized generic like `Sequence[T]` links a parameter's element type to the return type: whatever `T` turns out to be when the function is called, that's what comes back. `T = TypeVar('T')` is how you introduce that variable name — Python's `[]` syntax has no other way to declare it.

<details>
<summary>🧪 first() returns whatever type it was given</summary>

<PistonRunner
  lang="python"
  interactive={false}
  height="280px"
  code={`from collections.abc import Sequence
from typing import TypeVar

T = TypeVar('T')

def first(seq: Sequence[T]) -> T:
    return seq[0]

print(first([3, 1, 2]))
print(first('hello'))
print(first(('a', 'b', 'c')))
`}
/>

</details>

An unrestricted `TypeVar` accepts anything. `TypeVar('N', float, Decimal, Fraction)` **restricts** it to exactly those listed types. `TypeVar('H', bound=Hashable)` **bounds** it — any type is fine, as long as it's consistent-with `Hashable` — which is usually the more flexible and maintainable choice.

## Static protocols

A `typing.Protocol` subclass declares "any type with these methods counts" — no inheritance, registration, or explicit relationship required. That's **static duck typing**: it makes the informal "if it quacks like a duck" contract explicit enough for a type checker to verify. Decorate one `@runtime_checkable` and `isinstance()` will check it structurally too — purely by "does this object have the method," not by checking any declared relationship.

<details>
<summary>🧪 isinstance() against a Protocol, structurally</summary>

<PistonRunner
  lang="python"
  interactive={false}
  height="380px"
  code={`from typing import Protocol, runtime_checkable

@runtime_checkable
class SupportsQuack(Protocol):
    def quack(self) -> None: ...

class Duck:
    def quack(self):
        print('Quack!')

class Robot:
    def quack(self):
        print('Beep quack!')

class Cat:
    def meow(self):
        print('Meow!')

for obj in (Duck(), Robot(), Cat()):
    print(type(obj).__name__, isinstance(obj, SupportsQuack))
`}
/>

</details>

`Robot` never mentions `SupportsQuack` anywhere — no base class, no registration — yet `isinstance(Robot(), SupportsQuack)` is `True`, purely because it happens to define `.quack()`. That's the whole point: a `Protocol` lets pre-existing types, including ones you don't control, satisfy an interface just by shape.

## Callable, NoReturn, and annotated variadic parameters

`Callable[[ParamType1, ParamType2], ReturnType]` annotates a function passed as an argument — the list in `[]` is the parameter types, and `...` in place of that list means "any signature." `NoReturn` marks a function that never returns normally — it always raises. And the `*args`/`**kwargs` you met in Chapter 7 get typed too: `*content: str` means every item collected into `content` is `str`, and `**attrs: str` means `attrs` ends up as `dict[str, str]`.

## Chapter summary

:::important Key takeaways

1. Type hints are optional, unenforced at runtime, and give no performance boost — they exist purely for static tools.
2. Duck typing (runtime) and nominal typing (static) coexist in a gradual system; a type checker can flag code that runs correctly, and miss code that will crash.
3. `Any` opts an expression out of checking entirely; `object` accepts every value but supports almost no operations. `int` is consistent-with `float`, which is consistent-with `complex`.
4. `Optional[X]` means `Union[X, None]` — it does not by itself make a parameter optional; you still need `= None`.
5. Generic collections use `[]` directly (`list[str]`, `dict[str, set[str]]`) since Python 3.9. Annotate parameters with abstract types (`Mapping`, `Sequence`, `Iterable`); keep return types concrete.
6. Tuples get three annotation styles: fixed record (`tuple[str, float]`), named record (`NamedTuple`), and variable-length uniform (`tuple[int, ...]`).
7. `TypeVar` links a parameter's element type to the return type in a generic function; restrict it to a closed list of types, or bound it to anything consistent-with an ABC like `Hashable`.
8. `typing.Protocol` (optionally `@runtime_checkable`) makes duck typing explicit and checkable — no inheritance required, just matching methods.
9. `Callable[[...], R]` types a function argument; `NoReturn` marks a function that always raises; `*args`/`**kwargs` can be typed per-item.
10. Type hints catch real bugs in large codebases, but they produce false positives and negatives, can't express most business-logic constraints ("quantity must be > 0"), and are never a substitute for automated tests.

:::
