  <Problem
    type="concept"
    title="7.1"
    company="Robinhood"
    minWords={20}
    keywords={['precision', 'recall']}
    prompt={`You are building a binary classifier for an unbalanced dataset (say the positive class is 1% and the negative class is 99%). How do you handle this?`}
    answer={`Work through the toolkit roughly in order of effort. First, see whether more data for the rare class is available — cheap and easy to overlook. Next, fix the evaluation metric: accuracy is misleading here, since "always predict negative" already scores 99%; use precision $=\\frac{TP}{TP+FP}$, recall $=\\frac{TP}{TP+FN}$, F1, or a precision-recall / ROC curve instead. Then try resampling — oversample the rare class or undersample the abundant one (bootstrapping makes both easy), or generate synthetic minority examples with SMOTE (interpolating between a rare point and its nearest rare neighbors). You can also train an ensemble of models on different class ratios, or simply move the decision threshold off the default 0.5 to trade precision for recall — some models (logistic regression among them) already handle imbalance reasonably well without resampling. As a last, more involved resort, build a custom cost-sensitive loss that penalizes misclassifying the rare class more heavily than the common one.`}
  />
  <Problem
    type="concept"
    title="7.2"
    company="Square"
    minWords={15}
    keywords={['outlier']}
    prompt={`What differences would you expect between a model that minimizes squared error (MSE) versus one that minimizes absolute error (MAE)? When is each metric appropriate?`}
    answer={`Both measure average prediction error in units of the target and range from $0$ to $\\infty$ (lower is better), but MSE squares each error before averaging, so large errors get weighted disproportionately more than small ones — MAE weights every error linearly instead. That makes MSE sensitive to outliers and MAE comparatively robust to them. MSE is also easier to optimize: its gradient is a simple linear function of the residual, while MAE's gradient is a constant $\\pm 1$ (the derivative is undefined at zero), making exact MAE minimization a bit fiddlier. Statistically, MSE is minimized by the conditional mean and corresponds to maximum-likelihood estimation under Gaussian-distributed errors; MAE is minimized by the conditional median and doesn't correspond to a Gaussian likelihood. Net: reach for MAE when the data has outliers you don't want dominating the fit, and MSE when large errors are genuinely worse (or you want the easier optimization problem).`}
  />
  <Problem
    type="concept"
    title="7.3"
    company="Facebook"
    minWords={15}
    keywords={['elbow', 'silhouette']}
    prompt={`When performing k-means clustering, how do you choose k?`}
    answer={`The elbow method plots within-cluster sum-of-squared-error (distortion) against $k$: the first few clusters explain a lot of variation, but returns diminish past some point, producing a visible "elbow" — pick $k$ there. It's a heuristic, not a guarantee: the curve sometimes decreases smoothly with no obvious bend. A more principled (and more expensive) alternative is the silhouette method, which for each point compares its mean distance to points in its own cluster ($y$) against its mean distance to the nearest other cluster ($x$): $s = \\frac{x - y}{\\max(x, y)}$, ranging from $-1$ (wrong cluster) to $1$ (well-clustered). Average $s$ over all points for each candidate $k$ and pick the $k$ that maximizes it. In practice, business intuition often beats both — if you're segmenting customers, stakeholders usually have a rough prior on how many groups should exist, and you can sanity-check by visualizing feature distributions across the resulting clusters.`}
  />
  <Problem
    type="concept"
    title="7.4"
    company="Salesforce"
    minWords={15}
    keywords={['regularization']}
    prompt={`How can you make your models more robust to outliers?`}
    answer={`Start by investigating *why* the outliers occurred — that shapes which fix is appropriate. Options, roughly least to most invasive: add regularization (L1/L2) to shrink coefficients and reduce variance; switch to a model family that's naturally less sensitive to outliers, like tree-based ensembles (random forests, gradient boosting) instead of linear models; Winsorize the data by capping extreme values at a percentile (e.g. clip the top/bottom 5% to the 95th/5th percentile); transform the target, e.g. a log transform when it's right-skewed or roughly exponential; or swap the loss/error metric for something more robust, like MAE or Huber loss in place of MSE. Only remove outliers outright as a last resort, and only once you're confident they're genuine data errors rather than real (if rare) signal — dropping data throws away information about the true variability.`}
  />
  <Problem
    type="concept"
    title="7.5"
    company="AQR"
    minWords={20}
    keywords={['multicollinearity']}
    prompt={`Say you're running a multiple linear regression and suspect several predictors are correlated. How will the results be affected, and how would you deal with it?`}
    answer={`This is multicollinearity, and it causes two main problems. First, coefficient estimates (and even their signs) become unstable and sensitive to exactly which correlated variables you include — the effect gets "split" across the correlated predictors, so confidence intervals widen and can straddle zero even for a variable that genuinely matters. Second, p-values become misleading: a truly important predictor can look statistically insignificant because its explanatory power is shared with a correlated partner. To deal with it, either remove or combine the correlated predictors — first understand *why* they're correlated (did you include a variable and a near-duplicate of it, like $X$ and $2X$, or is there a latent factor driving both?) before deciding which to drop. To combine rather than drop, add an interaction term (their product), or reduce dimensionality with something like PCA. You can also center the variables, collect more data to narrow the intervals, or apply regularization — ridge regression in particular shrinks correlated coefficients together rather than letting them swing wildly.`}
  />
  <Problem
    type="concept"
    title="7.6"
    company="Point72"
    minWords={15}
    keywords={['bagging']}
    prompt={`Describe the motivation behind random forests. What are two ways in which they improve upon individual decision trees?`}
    answer={`A single decision tree grown deep enough can memorize the training set — split until every leaf is (near) pure and you've essentially fit noise, which generalizes poorly. Random forests fight this with two mechanisms. First, bagging: each tree trains on an independent bootstrap resample of the rows, and predictions are averaged (or majority-voted); averaging $B$ roughly-independent noisy trees shrinks prediction variance on the order of $\\sigma^2/B$ without touching bias. Second, feature subsampling ("mtry"): at every split, only a random subset of $m<p$ features is even eligible, which decorrelates the trees — without it, the same one or two dominant features would sit at the top of nearly every tree (since they maximize information gain), keeping the trees highly correlated and limiting how much averaging can help. Together these give solid out-of-the-box accuracy, fast parallel training (trees are independent), and interpretable feature importances, at the cost of some transparency versus a single tree.`}
  />
  <Problem
    type="concept"
    title="7.7"
    company="PayPal"
    minWords={20}
    keywords={['impute']}
    prompt={`Given a large dataset of payment transactions, you want to predict whether a transaction is fraudulent — but many rows have missing values across various columns. How would you deal with this?`}
    answer={`Start by clarifying the missing-data pattern before jumping to imputation: is it uniform across features, numeric or categorical, and is it missing completely at random, missing at random (given other observed fields), or not-missing-at-random (the missingness itself is informative, e.g. fraudsters spoofing certain fields)? That framing decides the fix. Then establish a baseline: build a model that simply drops or ignores the missing feature(s) and see if it already clears the bar — missing data isn't automatically a problem if it's concentrated in low-signal columns (a user's middle name) rather than high-signal ones (IP-derived geolocation). If imputation is worth it, start simple — mean/median for numeric features — then move to something that uses correlations across features, like k-nearest-neighbors imputation, and cross-validate to confirm it actually improves performance versus the baseline (a lift only shows up if the missing feature carries real signal for the rows that have it). Beyond that, consider whether a third-party dataset can backfill a column (e.g. inferring merchant category from an address via a business-listings dataset), and remember that some model families (certain tree implementations) handle missing values natively without requiring imputation at all.`}
  />
  <Problem
    type="concept"
    title="7.8"
    company="Airbnb"
    minWords={15}
    keywords={['regularization']}
    prompt={`Say you're running a simple logistic regression to solve a problem but find the results unsatisfactory. What are some ways you might improve your model, or what other models might you look into instead?`}
    answer={`Within logistic regression: normalize/standardize features so no single scale dominates the weights; add more informative features, since logistic regression is high-bias and usually benefits from richer inputs; look for and address outliers; do feature selection to strip out noisy variables; and use k-fold cross-validation with hyperparameter tuning, particularly a regularization penalty (L1/L2), to control overfitting. If none of that closes the gap, the underlying issue may be that the classes aren't linearly separable — logistic regression only draws a linear decision boundary — in which case look at SVMs with a nonlinear kernel, tree-based ensembles (random forests, gradient boosting), or neural networks, all of which can capture nonlinear boundaries at some cost to interpretability and training/data requirements.`}
  />
  <Problem
    title="7.9"
    company="Two Sigma"
    decimals={0}
    prompt={`You're running a simple linear regression, but you accidentally duplicated every data point before fitting (each row now appears exactly twice). What is the ratio of the new fitted coefficient $\\hat\\beta$ to the original one — i.e. by what factor does $\\hat\\beta$ change?`}
    answer={1}
    why={`Recall the closed-form OLS estimator $\\hat\\beta = (X^\\top X)^{-1}X^\\top y$. Duplicating every row stacks $X$ on top of itself, so $X_{\\text{dup}}^\\top X_{\\text{dup}} = 2\\,X^\\top X$ and $X_{\\text{dup}}^\\top y_{\\text{dup}} = 2\\,X^\\top y$ — both scale by exactly 2. Plugging in: $\\hat\\beta_{\\text{dup}} = (2X^\\top X)^{-1}(2X^\\top y) = (X^\\top X)^{-1}X^\\top y = \\hat\\beta$. The factor of 2 cancels, so the coefficient is completely unchanged (ratio $=1$) — duplicating rows adds no new information, it just (wrongly) inflates your apparent sample size and shrinks standard errors.`}
  />
  <Problem
    type="concept"
    title="7.10"
    company="PWC"
    minWords={20}
    keywords={['sequential']}
    prompt={`Compare and contrast gradient boosting and random forests.`}
    answer={`Both are ensembles of decision trees that need little preprocessing, but they differ structurally in two ways. First, tree construction: gradient boosting builds trees one at a time, where each new tree learns to correct the errors (residuals) of the ensemble so far, while random forest trees are built independently and in parallel from bootstrap samples. Second, combination: boosting blends weak learners additively as it goes (each tree's contribution is added to a running prediction), while a random forest only combines trees at the end, via averaging or majority vote. These differences have consequences — boosting's focus on mistakes and lack of independence between trees make it more prone to overfitting (mitigated with learning-rate shrinkage, tree-depth limits, and early stopping) and generally harder to tune, and it can't parallelize across trees the way a forest can. In practice, gradient boosting tends to shine on imbalanced problems like fraud detection, while random forests are a strong, low-fuss default for noisy multi-class problems.`}
  />
  <Problem
    type="concept"
    title="7.11"
    company="DoorDash"
    minWords={20}
    keywords={['learning curve']}
    prompt={`DoorDash is launching in Singapore and wants to predict delivery ETA. From an earlier beta test there were 10,000 deliveries made. Do you have enough training data to build an accurate ETA model?`}
    answer={`"Accurate enough" is subjective, so start by clarifying what the ETA prediction is used for — the accuracy bar for order-driver matching is probably tighter than what's shown to the customer in-app, and it's worth asking whether the business would rather under-promise (customers pleasantly surprised) or risk over-promising (customers bailing to pick up themselves). One data-driven anchor: look at ETA-model performance in comparable existing markets to estimate the business cost of over/under-shooting. Then fit a simple baseline on the 10,000-delivery beta set (e.g. driving time plus average prep time by restaurant/time-of-day) and evaluate with RMSE, MAE, or $R^2$. To judge whether *more* data would meaningfully help, plot a learning curve — model performance (say $R^2$) as a function of training-set size. If performance is still climbing steeply near 10,000 rows, more data would likely help a lot; if it has flattened, the bottleneck is probably features or model choice, not sample size. If the learning curve says data is genuinely the constraint, options include adding features (marketplace supply/demand, live traffic), checking whether there are too many features relative to rows (risking overfitting — consider dimensionality reduction or feature selection), trying models that need less data, and weighing whether launching now (and retraining as real Singapore data accumulates) is acceptable given the business timeline.`}
  />
