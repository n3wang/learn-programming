## Systems design (8.34–8.35)

<ProblemSet id="ds-sql-medium-design-8">
  <Problem
    type="concept"
    title="8.34"
    company="Facebook"
    minWords={55}
    keywords={['map', 'intersection']}
    prompt={`Given the Facebook friendship graph, how would you use MapReduce to count mutual friends for every pair of users?`}
    answer={`Goal: for every unordered pair (X, Y), count friends in common. Map: for each user X with friend list F, emit for every friend Z a key that is the sorted pair (X, Z) with value F (X's full friend list). After shuffle, each pair key collects the friend lists of both endpoints. Reduce: intersect the two friend lists and emit the intersection size as the mutual-friend count. Sorting the pair in the key avoids counting (X,Y) and (Y,X) twice. This parallelizes pairwise intersections; in practice you still need care for huge degree, skewed hubs, and whether you want mutual friends of all pairs or only pairs that are already friends.`}
  />
  <Problem
    type="concept"
    title="8.35"
    company="Google"
    minWords={55}
    keywords={['shard', 'hash']}
    prompt={`Design a large-scale system that tracks search query strings and their frequencies. What trade-offs matter?`}
    answer={`Start with a key-value (or wide-column) store: key = query string, value = count (or count + sketch). At Google scale, prefer horizontal sharding over vertical scaling. Range sharding by first letter is simple but skews load toward common prefixes; hash sharding balances better but makes ordered scans harder and complicates adding nodes unless you use consistent hashing. Writes are high-rate increments — batch or use counters/CRDTs; reads may need caching for hot queries. Trade-offs: exact counts vs approximate (Count-Min / HyperLogLog for related metrics), consistency of increments under failure, storage of long-tail queries, and whether you keep raw logs for reprocessing. Also plan secondary indexes if you need top-N queries without a full scan.`}
  />
</ProblemSet>
