> **Source:** Problem prompts adapted from *Ace the Data Science Interview* — Chapter 8 Easy set (Huo & Singh). Seeds, SQLite solutions, and model answers here are original for this course.

Thirteen query drills plus eight short design/systems write-ups. Each SQL exercise ships its **own seed database** (≥15 rows per table where the prompt allows). Open the **Data** tab, write only a `SELECT` / `WITH … SELECT`, then **Check**. Runtime is **SQLite** via the wrap-seed runner — use `CASE` instead of Postgres `IF`, `strftime` / `date()` instead of `DATE_TRUNC` / `INTERVAL` when you need date math, and prefer `LEFT JOIN` over `RIGHT JOIN`.

Hints: restating the metric (“CTR = clicks / impressions in 2019”) before coding beats jumping into `GROUP BY`. Column names match the prompt schemas below.

## Design & concepts (8.14–8.21)

Written answers — use the keywords when shown, then compare to the model answer.

<ProblemSet id="ds-sql-easy-concepts-8">
  <Problem
    type="concept"
    title="8.14"
    company="Facebook"
    minWords={40}
    keywords={['view', 'query']}
    prompt={`What is a database view? Name advantages views can have compared with base tables.`}
    answer={`A view is a named query stored in the catalog: when you SELECT from it, the engine runs (or materializes) that query against underlying tables. It usually has no independent physical row store of its own (unless it is a materialized view). Advantages: (1) hide join/filter complexity behind a stable name; (2) expose only selected columns/rows for security; (3) avoid duplicating large derived tables when a logical definition is enough; (4) keep consumers insulated if you later change how the view is computed. Trade-off: poorly indexed underlying tables can make views slow, and nested views can become hard to reason about.`}
  />
  <Problem
    type="concept"
    title="8.15"
    company="Expedia"
    minWords={45}
    keywords={['index', 'write']}
    prompt={`If most queries are UPDATE/INSERT/DELETE, how does that affect indexing? What if most queries are SELECT/JOIN instead?`}
    answer={`Every index is another structure that must stay in sync on writes, so heavy OLTP mutation workloads usually want fewer, carefully chosen indexes — otherwise inserts/updates/deletes pay for maintaining each secondary index. Read-heavy analytical or reporting workloads (many SELECT/JOIN scans and filters) benefit from more indexes that support common predicates and join keys, because reads do not rewrite those structures. In short: write-heavy → lean indexes; read-heavy → index for access paths, accepting write and storage cost.`}
  />
  <Problem
    type="concept"
    title="8.16"
    company="Microsoft"
    minWords={35}
    keywords={['unique', 'null']}
    prompt={`What is a primary key? What makes a good primary key?`}
    answer={`A primary key uniquely identifies each row in a table. It may be one column or a composite of several, and its values must be unique and not NULL. A good key is stable (does not change as business attributes change), unique, and irreducible (no proper subset of its columns is already unique). Surrogate keys (e.g., integer ids) are common when natural keys are long, mutable, or privacy-sensitive.`}
  />
  <Problem
    type="concept"
    title="8.17"
    company="Amazon"
    minWords={50}
    keywords={['ACID', 'schema']}
    prompt={`Compare advantages and disadvantages of relational databases versus NoSQL stores.`}
    answer={`Relational DBs shine with a fixed schema, rich joins, and ACID transactions — strong integrity for money, inventory, and multi-row updates, plus a standard SQL skill set. They are harder to shard horizontally at extreme scale and schema migrations on huge tables can be painful. NoSQL (document, key-value, wide-column, graph) often offers flexible documents, easier horizontal scale, and high availability under BASE/eventual consistency, which fits rapidly changing product schemas and massive read/write fan-out. Downsides: weaker multi-record transactions, more application-side consistency logic, and query patterns that are awkward without the right access model. Pick based on consistency needs and access patterns, not fashion.`}
  />
  <Problem
    type="concept"
    title="8.18"
    company="Capital One"
    minWords={40}
    keywords={['map', 'random']}
    prompt={`At a high level, how would a MapReduce job implement a shuffle that randomly reorders a dataset?`}
    answer={`Map each input row to a random key (for example an integer in 1…k for k reducers, or a random hash), emitting (random_key, row). The shuffle groups by that key so each reducer receives a random subset of rows. The reduce step simply writes the rows out (optionally sorting within the reducer by another random). Because assignment to reducers is random, the concatenated output is a randomly ordered version of the input. True global random order may still need a final merge or a second pass if you need a single fully shuffled stream.`}
  />
  <Problem
    type="concept"
    title="8.19"
    company="Amazon"
    minWords={30}
    keywords={['WHERE', 'HAVING']}
    prompt={`Name one major similarity and one major difference between WHERE and HAVING in SQL.`}
    answer={`Similarity: both filter which results you keep — they are optional predicates that shrink the result set. Difference: WHERE filters rows before aggregation (you cannot reference aggregate results in WHERE), while HAVING filters after GROUP BY and can use aggregates like COUNT(*) or SUM(x). In practice, put row filters in WHERE and group-level filters in HAVING.`}
  />
  <Problem
    type="concept"
    title="8.20"
    company="KPMG"
    minWords={35}
    keywords={['foreign key', 'primary']}
    prompt={`What is a foreign key, and how does it relate to a primary key?`}
    answer={`A foreign key is a column (or set of columns) in a child table whose values must match a primary key (or unique key) in a parent table. It enforces referential integrity: you cannot insert a child row that points at a missing parent, and you control what happens on parent deletes/updates (cascade, restrict, set null). Cardinality (1:1, 1:N, N:M) guides how you place the FK — N:M usually needs a junction table with two foreign keys.`}
  />
  <Problem
    type="concept"
    title="8.21"
    company="Microsoft"
    minWords={45}
    keywords={['clustered', 'pointer']}
    prompt={`Compare clustered and non-clustered indexes.`}
    answer={`A clustered index defines the physical order of rows on disk (or in the leaf of the primary B-tree); there is typically only one per table because data can only be stored in one order. Range scans on the clustered key are very fast. A non-clustered index is a separate structure: it stores the indexed keys plus a pointer (row locator / clustering key) back to the heap or clustered leaf. You can have many non-clustered indexes. They speed selective lookups but add write cost and storage; lookups may need a key lookup into the base table unless the index covers the query.`}
  />
</ProblemSet>
