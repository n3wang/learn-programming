# Mechanism: Limited Direct Execution

To virtualize the CPU the OS must **time-share** it — run one process awhile, then another. Two constraints collide:

| Goal | Fear |
|---|---|
| **Performance** | Emulating every instruction would be too slow |
| **Control** | A process must not run forever or touch forbidden resources |

**Crux:** how to virtualize the CPU **efficiently** while the OS **keeps control**?

**Answer:** **limited direct execution (LDE)** — run the program *directly* on the hardware CPU, but with hardware + OS limits so the kernel stays in charge.

## Direct execution (no limits yet)

Without limits the protocol is almost a library call:

1. Create process entry, allocate memory, load code  
2. Jump to `main()`  
3. Process returns → OS frees resources  

Fast — but two problems remain:

1. How does a process do **restricted** work (I/O, …) without owning the machine?  
2. How does the OS **stop** a running process to switch to another?

Without limits, the OS is “just a library.”

## Problem 1: restricted operations

### User mode vs kernel mode

| Mode | Who | Power |
|---|---|---|
| **User** | Apps | Restricted — illegal I/O → exception (often kill the process) |
| **Kernel** | OS | Full privileges — I/O, timers, trap-table install, … |

### System calls = controlled entry

User code requests services via **system calls** (`open`, `read`, `fork`, …). Under the hood:

1. C library places **syscall number** + args in agreed registers/stack  
2. Executes a **trap** instruction  
3. Hardware: save regs → **kernel stack**, raise privilege, jump to OS handler from the **trap table**  
4. OS validates args (**never trust user pointers**), does the work  
5. **return-from-trap** → user mode, resume after the trap  

User code must **not** pick an arbitrary kernel address — only a syscall number. The trap table is installed at **boot** (privileged).

:::tip Protected control transfer
Hardware provides modes + trap / return-from-trap + a place to register handlers. That is how speed and safety coexist.
:::

## Problem 2: switching processes

If a process is on the CPU, the OS is **not**. So how can the OS decide to switch?

### Cooperative approach

Trust processes to give the CPU back via syscalls (or a `yield`), or when they fault. Early Mac OS / Xerox Alto style.

**Failure mode:** infinite loop with no syscall → only fix is often a **reboot**.

### Non-cooperative: timer interrupt

At boot the OS:

1. Registers a **timer interrupt** handler  
2. Starts a hardware timer (privileged)

Every few ms the timer fires → hardware saves state → OS runs. Now the kernel can preempt, schedule, and **context switch**.

### Context switch (idea)

When the scheduler picks another process:

1. **Hardware** already saved user regs of the interrupted process (on its kernel stack)  
2. **OS** saves kernel regs into that process’s PCB; restores the next process’s; switches kernel stacks  
3. **return-from-trap** resumes the *other* process  

Two save/restore layers: hardware (user → kernel) and software (process A ↔ B).

## Homework lab: measure syscall & context-switch cost

Measurement homework (OSTEP): time a null system call and estimate a context switch on a real UNIX-like machine. Notes/screenshots stay in **this browser**.

<GuidedLab id="ostep-lde-measure" title="Homework: measure syscall & context switch">
  <LabStep title="Timer precision">
    Measure back-to-back calls to `gettimeofday()` (or a higher-resolution clock). How precise is your timer really? That tells you how many iterations you need for a trustworthy average.
  </LabStep>
  <LabStep title="Null system call">
    Repeatedly call a cheap system call (e.g. a 0-byte `read`) and time the loop. Divide by iterations to estimate syscall cost. Use enough iterations given your timer precision.
  </LabStep>
  <LabStep title="Optional: rdtsc">
    If `gettimeofday()` is too coarse, try `rdtsc` (x86) or another cycle counter. Compare results to the timeval-based measurement.
  </LabStep>
  <LabStep title="Context switch via pipes">
    Recreate the lmbench-style idea: two processes on **one CPU**, two pipes, ping-pong reads/writes so each blocking read forces a switch. Measure many round trips and estimate cost per switch.
  </LabStep>
  <LabStep title="CPU affinity">
    On multicore machines, bind both processes to the same CPU (e.g. Linux `sched_setaffinity`) so you measure a real switch, not two cores chatting. Record your method and numbers.
  </LabStep>
</GuidedLab>

## Concurrency teaser

What if a timer fires **during** a syscall? Or one interrupt during another? The OS must protect itself (e.g. briefly **disable interrupts**, locks). Full story: concurrency chapters later.

## Summary

| Term | Meaning |
|---|---|
| **Limited direct execution** | Run natively, with limits |
| **User / kernel mode** | Restricted vs privileged |
| **Trap / return-from-trap** | Enter / leave the kernel safely |
| **Trap table** | Boot-time map of handlers |
| **System call** | Request a numbered kernel service |
| **Timer interrupt** | Preempt without cooperation |
| **Context switch** | Save one process, restore another |
