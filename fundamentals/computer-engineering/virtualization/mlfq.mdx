# Scheduling: The Multi-Level Feedback Queue

**MLFQ** (Corbató et al., CTSS, 1962) is one of the classic schedulers. Many modern systems still use a relative of it.

**Goals (without knowing job length up front):**

| Goal | Classic approach | Problem |
|---|---|---|
| Good **turnaround** | SJF / STCF (short jobs first) | OS rarely knows length — see [Scheduling Introduction](./scheduling-introduction) |
| Good **response** time | Round robin | Terrible turnaround for long jobs |

**Crux:** how to schedule **without perfect knowledge** — learn from how jobs behave?

:::tip Learn from history
MLFQ predicts the future from the past (like caches and branch predictors). Works when jobs have phases — and can be wrong when they don’t.
:::

## Basic structure

Many **queues**, each a **priority**. A ready job sits on exactly one queue.

- **Rule 1:** Higher priority runs; lower does not.  
- **Rule 2:** Same priority → **round-robin** with that queue’s time slice.

Priority is **not** fixed: MLFQ **raises/lowers** it from observed behavior (interactive vs CPU hog).

## Attempt #1: how priority changes

Workload mix: short/interactive + long CPU-bound.

- **Rule 3:** New job → **top** queue (assume it might be short).  
- **Rule 4a (old):** Uses full time slice → **demote** one level.  
- **Rule 4b (old):** Gives up CPU early → **stay** at same level.

**Effects:**

1. **Long job** — enters top, burns slices, sinks to bottom, stays there.  
2. **Short job arrives** — starts high, finishes before sinking far → approximates **SJF**.  
3. **I/O-heavy interactive** — often yields early → stays high → good **response** time.

### Flaws

| Problem | Why |
|---|---|
| **Starvation** | Too many interactive jobs → long jobs never run |
| **Gaming** | Fake I/O just before slice ends → stay high forever |
| **Phase change** | CPU-bound job becomes interactive but is stuck low |

Scheduling policy is also a **security** concern in shared systems.

## Attempt #2: priority boost

- **Rule 5:** Every period **S**, move **all** jobs to the topmost queue.

Fixes starvation and gives reformed interactive jobs a second chance. **S** is a classic “voo-doo constant” (Ousterhout): too large → starve; too small → interactive share suffers.

## Attempt #3: better accounting

Replace 4a/4b with:

- **Rule 4:** Once a job uses up its **CPU allotment** at a level (one burst or many), **demote** — I/O games don’t reset the meter.

## Tuning

Typical extras:

- **Shorter quanta** at high priority; **longer** at low (batch efficiency)  
- Solaris TS: configurable tables (~60 queues, boost ~1 s)  
- Some systems: decay-usage formulas (BSD), reserve top for OS, user **advice** (`nice`)

:::tip Avoid voo-doo constants
Hard in practice — defaults + admin knobs are common. Prefer learning parameters when you can.
:::

## Refined MLFQ rules

1. Higher priority runs.  
2. Same priority → RR with that queue’s quantum.  
3. New jobs start at the top.  
4. Exhaust allotment at a level → demote (cumulative CPU).  
5. Periodically boost everyone to the top.

**Result:** learn job type online → short/interactive get good service; long jobs still make progress.

## Summary

| Idea | Role |
|---|---|
| Multiple priority queues | Who is eligible |
| Feedback / history | Learn short vs long vs interactive |
| Boost every S | No starvation; phase changes |
| Cumulative allotment | Resist gaming |
| Varying quanta | Latency high, throughput low |
