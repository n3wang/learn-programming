# Scheduling: Proportional Share

Instead of optimizing turnaround or response time, a **proportional-share** (fair-share) scheduler tries to give each job a **target fraction** of the CPU.

**Crux:** how do we share the CPU proportionally — and how well do the mechanisms work?

Classic answers: **lottery** (random), **stride** (deterministic), and Linux **CFS** (vruntime + weights).

## Tickets = your share

If A has 75 tickets and B has 25, A should get ~75% of the CPU.

**Lottery scheduling** (Waldspurger & Weihl): every time slice, draw a winning ticket in `[0, total)`. Whoever holds that ticket runs.

- Probabilistically correct over long runs  
- Short runs can look unfair  
- Almost no state beyond ticket counts  

:::tip Use randomness
Random decisions often avoid pathological corner cases, need little state, and are fast if RNG is cheap.
:::

### Ticket tricks

| Mechanism | Idea |
|---|---|
| **Currency** | User assigns tickets in a private currency; OS converts to global shares |
| **Transfer** | Hand tickets to a server while it works for you, then take them back |
| **Inflation** | Temporarily raise your tickets — only safe among **trusting** processes |

### Implementation sketch

Walk a process list, accumulate tickets until `counter > winner`. Sorting high-ticket jobs first is an optimization, not required for correctness.

## Fairness study

Two equal-ticket equal-length jobs: unfairness *U* = *t*<sub>first</sub> / *t*<sub>second</sub> (ideal *U* ≈ 1). For short *R*, lottery can be quite unfair; as jobs run longer, *U* approaches 1.

**Open problem:** how many tickets should each job get? Users/admins often decide — the “ticket assignment problem” remains hard.

## Stride scheduling

Deterministic fair share:

1. `stride ∝ 1 / tickets` (e.g. `10000 / tickets`)  
2. Each job has a **pass** value (global progress)  
3. Always run the job with **minimum pass**  
4. After a quantum: `pass += stride`

Exact proportions over a cycle. Downside vs lottery: **global state** — a new job with `pass = 0` would monopolize; lottery just adds tickets and updates the total.

## Linux Completely Fair Scheduler (CFS)

Widely deployed fair-share scheduler. Goal: divide the CPU evenly (or by weight) with **low overhead** (scheduling alone can be ~5% of datacenter CPU in studies).

### Virtual runtime

- Each runnable job accumulates **vruntime** while it runs  
- Always pick the job with the **lowest vruntime**  
- Runnable jobs live in a **red-black tree** keyed by vruntime → \(O(\log n)\)  

### Dynamic slice

- `sched_latency` (e.g. 48 ms) / \(n\) ≈ ideal slice so fairness holds over that window  
- `min_granularity` (e.g. 6 ms) floors the slice so too many jobs don’t thrash on context switches  

### Nice → weight

`nice` from −20 (more CPU) to +19 (less). Weights scale both the effective slice and how fast vruntime grows (heavier weight → vruntime climbs slower → runs more). Constant nice *differences* preserve the same ratios.

### Sleep / I/O

A job that slept a long time would otherwise wake with tiny vruntime and hog the CPU catching up. CFS sets a waking job’s vruntime near the **current tree minimum** — avoids starvation of others (but short frequent sleepers may get less than “fair”).

## Summary

| Approach | How share is enforced | Tradeoff |
|---|---|---|
| **Lottery** | Random ticket draw | Simple; approximate; easy joins |
| **Stride** | Min pass += stride | Exact; awkward new-job state |
| **CFS** | Min vruntime + nice weights | Production Linux; RB-tree; I/O edge cases |

Fair-share leaves **ticket/nice assignment** hard and can interact poorly with I/O. Still excellent when shares are clear (e.g. VMs in a cloud).
