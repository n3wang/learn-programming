# Paging: Faster Translations (TLBs)

Paging needs a mapping for every page — usually in memory — so a naive design does an **extra memory lookup** before every fetch/load/store. That is prohibitively slow.

**Crux:** how speed up address translation and avoid that extra reference? What hardware help? What OS involvement?

## The TLB

A **translation-lookaside buffer (TLB)** is a small, fast **hardware cache of popular VPN→PFN translations** inside the MMU (better name: address-translation cache) [CG68, C95].

On each virtual reference:

1. Extract **VPN**  
2. **TLB_Lookup(VPN)**  
3. **Hit** → check protect bits → form PA → AccessMemory  
4. **Miss** → find PTE (hardware walk or OS trap) → **TLB_Insert** → **retry** the instruction  

Hits are cheap (near the core). Misses re-impose paging’s cost. Goal: **high hit rate**.

## Hardware-managed vs software-managed

| Style | On miss | Example |
|---|---|---|
| **Hardware-managed** | MMU walks page table via PTBR, fills TLB, retries | x86 (`CR3`) |
| **Software-managed** | Raise `TLB_MISS`; OS handler fills TLB with privileged ops; return-from-trap **retries same PC** | MIPS R10k, SPARC v9 |

Software-managed: OS can use **any** page-table structure; hardware stays simple. Watch out for **infinite miss loops** in the handler — keep handlers unmapped/physical or use **wired** TLB slots always resident.

:::info TLB valid ≠ page-table valid
**PTE invalid** → page not allocated; usually kill the process.  
**TLB valid** → this cache slot holds a usable translation. Empty at boot; filled as programs run. Clearing valid bits also **flushes** the TLB on a context switch.
:::

## Example: accessing an array

10× 4-byte ints starting at VA **100**. 8-bit VA space, **16-byte** pages → 4-bit VPN + 4-bit offset.

| Elements | VPN |
|---|---|
| a[0]…a[2] | 06 |
| a[3]…a[6] | 07 |
| a[7]…a[9] | 08 |

Trace for `sum += a[i]`: **miss, hit, hit, miss, hit, hit, hit, miss, hit, hit** → **70% hit rate** on the first pass — **spatial locality** (dense packing on pages). Larger pages → fewer misses. A second pass can approach **100%** if translations stay cached — **temporal locality**.

:::tip Use caching when possible
Caches exploit **temporal** (re-access soon) and **spatial** (nearby addresses) locality. Physics limits size: big → slow. Keep TLBs small and fast.
:::

## What’s in a TLB entry?

Typically **32–128** entries, **fully associative** (any translation anywhere; parallel search):

```
VPN | PFN | valid | protect | ASID? | dirty? | …
```

## Context switches

Translations are **per-process**. P1 VPN10→PF100 and P2 VPN10→PF170 cannot both sit unlabeled in one TLB.

| Approach | Idea | Cost |
|---|---|---|
| **Flush** | Clear all valid bits on switch | Safe; next process cold-misses |
| **ASID** | Tag entries with address-space ID | Share TLB across processes; OS sets current ASID |

Shared code pages: different VPNs / ASIDs can map to the **same PFN** (read-execute).

## Replacement policy

On insert, evict someone:

- **LRU** — good with locality  
- **Random** — simple; avoids LRU’s pathology (loop over *n*+1 pages with TLB size *n* → LRU misses every time)

Exceeding **TLB coverage** (working set of pages &gt; TLB entries) → many misses. Larger pages raise coverage (next chapter).

## A real entry (MIPS R4000)

Software-managed TLB: VPN, PFN, **G** (global — ignore ASID), **ASID**, cache coherency bits, dirty, valid; **wired** slots reserved for the OS. Privileged ops: `TLBP`, `TLBR`, `TLBWI`, `TLBWR`.

:::tip Culler’s Law — RAM isn’t always RAM
Random access across more pages than the TLB covers can be **much** slower than sequential access within a few pages — even though “it’s all RAM.”
:::

## Homework lab: measure the TLB

Measurement homework (Saavedra-Barrera style [SB92]): time touching *N* pages in a loop and watch cost jumps as you exceed TLB capacity. Run on a real machine — not in the Piston sandbox.

<GuidedLab id="ostep-tlb-measure" title="Homework: measure TLB size & miss cost">
  <LabStep title="Timer precision">
    How precise is `gettimeofday()` (or a better clock)? How many loop iterations do you need for a trustworthy average?
  </LabStep>
  <LabStep title="Write tlb.c">
    Inputs: number of pages to touch, number of trials. Stride by `PAGESIZE / sizeof(int)` so you touch one int per page.
  </LabStep>
  <LabStep title="Sweep page counts">
    Script from 1 page up to a few thousand (×2 each time). Gather timing on one or more machines. How many trials for stable numbers?
  </LabStep>
  <LabStep title="Graph the jumps">
    Plot ns/access vs pages. Infer L1 TLB size, whether an L2 TLB exists, and miss cost ratios.
  </LabStep>
  <LabStep title="Defeat the optimizer">
    Ensure the compiler does not remove your loop (volatile, use the sum, `-O0` carefully). Document your approach.
  </LabStep>
  <LabStep title="Pin to one CPU">
    Bind the thread to a single core so the scheduler does not bounce you across CPUs (each with its own TLB). What goes wrong if you don’t?
  </LabStep>
  <LabStep title="Initialize first">
    Touch/zero the array before timing so demand-zero / first-touch costs do not dominate. Re-measure.
  </LabStep>
</GuidedLab>

## Summary

| Idea | One line |
|---|---|
| **TLB** | On-chip cache of VPN→PFN translations |
| **Hit / miss** | Hit skips page-table memory; miss walks or traps |
| **Locality** | Spatial + temporal → high hit rates |
| **HW vs SW miss** | Walk in hardware vs OS trap handler |
| **Context switch** | Flush or ASID-tag entries |
| **Replacement** | LRU vs random; watch TLB coverage |
| **Culler’s Law** | Random page access can thrash the TLB |
