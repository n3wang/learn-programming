# Event-based Concurrency (Advanced)

Threads are not the only way to build concurrent apps. GUIs [O96], some internet servers [PDZ99], and frameworks like **node.js** [N13] often use **event-based concurrency** — roots in classic C/UNIX `select`/`poll` servers.

**Crux:** how to build concurrent servers **without threads**, keep control of scheduling, and dodge many threading bugs?

## The event loop

```text
while (1) {
    events = getEvents();
    for (e in events)
        processEvent(e);   // one handler at a time
}
```

Handling an event is the only activity — so **choosing which event next = scheduling**. That explicit control is a main advantage.

## select() / poll()

Ask the OS which FDs are ready to read/write (or have errors). Typical loop: `FD_ZERO` → `FD_SET` interested sockets → `select` → `FD_ISSET` and `processFD`.

- `timeout = NULL` — block until ready  
- `timeout = 0` — poll and return immediately  

:::tip Don’t block in event-based servers
Any blocking call stalls the **entire** server. Non-blocking / async I/O is mandatory.
:::

## Why simpler? No locks (on one CPU)

One handler at a time, single-threaded → no other thread interrupts → **no locks** for shared state between handlers. Concurrency bugs from Ch. 32 largely vanish — until you go multicore.

## The problem: blocking system calls

A file-serving request needs `open`/`read`. Threads: one thread sleeps on I/O; others run. Events: the **only** loop blocks → idle waste.

## Solution: asynchronous I/O

Fill an **aiocb** (fd, offset, buf, nbytes), call `aio_read` — returns immediately. Poll completion with `aio_error` (or get a **signal** when done). Systems without good AIO often use a **hybrid**: events for network + thread pool for disk [PDZ99].

## Continuations (manual stack management)

Threads keep `sd` on the stack across `read(fd)` then `write(sd,…)`. Events must **package state** when issuing async I/O — a **continuation** [A+02,FHK84]: e.g. hash table `fd → {sd}`; on completion, look up and finish the write.

## What is still hard

| Issue | Why it hurts |
|---|---|
| **Multicore** | Parallel handlers → locks return |
| **Paging** | Implicit page-fault blocking stalls the loop |
| **API drift** | A routine becoming blocking forces handler rewrites |
| **Split I/O APIs** | Often `select` for net + AIO for disk — not one uniform wait |

## Summary

| Piece | Role |
|---|---|
| **Event loop** | Wait → handle one-at-a-time (= schedule) |
| **select/poll** | Which FDs are ready? |
| **No blocking** | Or the whole server stalls |
| **AIO / hybrid** | Overlap disk without a sleeping thread |
| **Continuations** | Manual stack across async steps |

Threads and events both persist — pick based on control, complexity, and platform I/O support [A+02, PDZ99, WCB01, vB+03].
