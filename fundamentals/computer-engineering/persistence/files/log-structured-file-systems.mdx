# Log-structured File Systems

Berkeley LFS [RO91] (Rosenblum & Ousterhout) aims for **write performance** by turning updates into **large sequential** transfers.

**Motivation**

- Bigger memories → more reads hit cache → disk traffic is **write-heavy**
- Sequential bandwidth ≫ random (seeks/rotations lag transfer rates)
- FFS still pays many small seeks for create/metadata updates
- Classic FSes ignore RAID **small-write** pain (RAID-4/5)

**Crux:** how can a file system make **all writes** sequential?

## Segments and write buffering

LFS buffers data **and** metadata in memory, then writes a **segment** (a few MB) to free space in one long I/O. It **never overwrites in place** (copy-on-write / shadow paging).

Sequential *addresses* alone aren’t enough — if you wait between block writes, the platter rotates. You need a **large contiguous** write to amortize positioning:

`Reffective = D / (Tposition + D/Rpeak)`. For fraction `F` of peak: `D = F · Rpeak · Tposition / (1 − F)`.

Example: 10 ms position, 100 MB/s, F = 0.9 → about **9 MB** per flush.

## Finding inodes: imap and CR

Inodes are no longer at fixed offsets — each update moves them. LFS adds an **inode map (imap)**: inode number → disk address of the latest inode. imap chunks are written **next to** the segment contents (not a fixed hot spot).

A fixed **checkpoint region (CR)** points at the latest imap pieces. CR is updated periodically (~30 s) so the write path stays sequential.

**Read path (cold):** CR → load imap → inode → (in)direct blocks — same I/O count as a classic FS once imap is cached.

**Directories** still store `(name, inum)`. When an inode moves, only the imap changes — this avoids the **recursive update problem** up the directory tree.

## Garbage collection (cleaning)

Old versions left behind are **garbage**. Cleaning runs **segment-by-segment**: read `M` segments, compact live blocks into `N < M` new segments, free the old — keeps large free regions for future sequential writes.

**Liveness:** segment summary stores `(inum, offset)` per block; live iff current inode still points at that address. Version numbers in imap short-circuit truncate/delete checks.

**Policy:** clean **cold** segments sooner; wait on **hot** ones (more blocks die). Cleaning cost was controversial early on [SS+95]; later work improved policies [MR+97].

## Crash recovery

- **Two CRs** (ends of disk), updated alternately with timestamped header/body/trailer → detect partial CR writes
- **Roll forward** from the last good CR along the log to recover recent segments

## Summary

| Idea | Role |
|---|---|
| **Segments** | Large sequential COW writes |
| **imap** | Find moving inodes; stop recursive dir updates |
| **CR** | Fixed root; periodic; dual CR for atomicity |
| **Cleaning** | Segment GC of garbage versions |
| **Legacy** | WAFL, ZFS, btrfs, SSD FTLs |
