# Flash-based SSDs

Solid-state storage has **no moving parts** — NAND flash transistors that retain charge across power loss. Fujio Masuoka’s flash (1980s) has quirks that make SSD design hard:

**Crux:** how to build a flash SSD despite expensive **erase** and **wear out** from repeated program/erase?

## Raw flash: bits → pages → blocks

| Term (flash) | Typical size | Role |
|---|---|---|
| **Cell** | 1–3 bits (SLC / MLC / TLC) | Charge level encodes value |
| **Page** | ~2–4 KB | Unit of **read** / **program** |
| **Erase block** | ~128–256 KB | Unit of **erase** (many pages) |

**Ops**

- **Read(page)** — tens of μs, roughly location-independent (true random access vs disk)
- **Erase(block)** — milliseconds; sets bits to 1; **destroys** all pages in the block
- **Program(page)** — ~100s μs; can only change 1→0 after erase; once VALID, must erase block to rewrite

States: INVALID → erase → ERASED → program → VALID. You cannot re-program a VALID page in place.

**Reliability:** wear out (~10k P/E MLC, ~100k SLC); read/program **disturb** on neighbors. Program pages low→high within a block to reduce disturb.

## From chips to a block device: the FTL

An SSD exposes a normal **logical block** interface. Internally: flash chips + SRAM (cache/maps) + controller. The **flash translation layer (FTL)** maps client reads/writes to read/erase/program, aiming for:

- Low **write amplification** (bytes written to flash / bytes from client)
- **Wear leveling** (spread P/E across blocks)
- Parallelism across chips

### Direct-mapped FTL (bad)

Logical N ↔ physical N. Every write: read whole erase block, erase, reprogram → terrible amp and hot-spot wear. Don’t do this.

### Log-structured FTL (common)

Append each write to the next free page; update an in-memory **LBA → physical** map. Erases happen when opening a new block; overwrites leave **garbage**.

**Garbage collection:** find blocks with dead pages, relocate live pages to the log, erase the old block. Ideal reclaim target: all-dead. **Overprovisioning** delays GC and hides cleaning bandwidth.

**TRIM:** host tells the device LBAs are unused → drop maps, reclaim earlier.

**Map persistence:** OOB metadata per page (slow full scan on boot) or logging/checkpoints (faster recovery).

### Mapping table size

Page-level maps need too much DRAM (e.g. ~1 GB for 1 TB @ 4 KB). Options:

| Scheme | Memory | Write pain |
|---|---|---|
| **Page map** | Huge | Flexible |
| **Block map** | Small | Small write → copy whole block |
| **Hybrid** | Log blocks page-mapped; data blocks block-mapped | **Switch / partial / full** merges |
| **Cached page map** (DFTL) | Only hot entries | Misses cost extra flash I/O |

### Wear leveling

Log + GC help, but **cold** long-lived data never frees its block. FTL must periodically migrate cold live data so every block gets write traffic — more write amp for fairness.

## Performance vs cost

SSDs crush HDDs on **random** IOPS; sequential gap is smaller. Log FTLs turn random client writes into sequential flash programs. HDDs still win **$/GB** → hybrid “hot on SSD, cold on disk” tiers remain common.

## Summary

| Idea | Takeaway |
|---|---|
| **Erase before program** | Page write ≠ disk overwrite |
| **FTL** | Block API atop weird flash ops |
| **Log FTL** | Append + map; GC + TRIM + wear leveling |
| **Map space** | Hybrid or cached page maps |
| **Market** | SSD for latency/IOPS; HDD for $/GB |
