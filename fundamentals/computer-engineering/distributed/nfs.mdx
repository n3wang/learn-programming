# Sun’s Network File System (NFS)

Clients talk to a **file server** that owns the disks. Why not only local disks?

- **Sharing** — same namespace from any client
- **Central admin** — backup a few servers, not every laptop
- **Security** — servers in a locked room

**Crux:** how do you build a distributed file system? What goes wrong?

## Architecture

Apps call the normal POSIX API (`open`, `read`, …). The **client-side file system** turns those into protocol messages; the **file server** serves them (disk or server cache). Transparent access: same API, (hopefully) similar behavior, remote data.

Sun published an **open protocol** (message formats) so many vendors could interoperate — a big reason NFS won [S86].

## Goal: fast server crash recovery → statelessness

When the server is down, every client is unhappy. NFSv2’s answer: a **stateless** protocol — the server does not remember open files, cursors, or which clients cache what. Each request carries **all** information needed to complete.

A stateful `open`→fd shared with the server is **distributed state** [O91]: server crash forgets fds; client crash leaves server opens orphaned. Recovery gets messy. Stateless: reboot the server; clients **retry**.

### File handles

`FH = (volume ID, inode #, generation #)`. Generation bumps when an inode is reused so stale handles cannot hit the wrong file.

| Call (sketch) | Client sends | Server returns |
|---|---|---|
| **LOOKUP** | dir FH + name | FH + attributes |
| **READ** | FH + offset + count | data + attributes |
| **WRITE** | FH + offset + count + data | attributes |
| **GETATTR** | FH | attributes (incl. mtime) |

`open("/foo")` → LOOKUP; successive `read(fd,…)` use the client’s fd→FH map and **local** offset. `close` is local — no server message.

## Idempotent retry

Timeouts: lost request, server down, or lost reply. NFSv2 treats them the same — **resend**.

**Idempotent** = doing it N times ≡ once. READ/LOOKUP yes; WRITE yes if it includes absolute offset + data. MKDIR is awkward (success + lost reply → retry “fails”). Voltaire’s Law: perfect is the enemy of the good.

## Client caching and consistency

Caching data (and buffering writes) is mandatory for speed — and creates the **cache consistency problem**:

1. **Update visibility** — C2’s dirty `F[v2]` still only in C2’s RAM
2. **Stale cache** — server has `F[v2]` but C1 still holds `F[v1]`

NFSv2 engineering:

- **Flush-on-close** (close-to-open): close forces dirty pages to the server so a later open elsewhere can see updates
- **Validate before use**: GETATTR; newer server mtime → invalidate cache
- **Attribute cache** (~few seconds) stops GETATTR storms — at the cost of fuzzy “which version?” semantics

## Server write buffering

The server **must not** ack WRITE success until data is on **stable storage**. Otherwise a crash after a buffered “success” can leave holes (client thinks `a,b,c` wrote; disk has `a`, old, `c`). Fast NFS appliances use battery-backed memory + write-optimized FS layouts [HLM94].

**VFS/vnode** [K86]: Sun’s pluggable FS interface so NFS could sit beside local FS — still everywhere.

## Summary

| Idea | Takeaway |
|---|---|
| **Stateless** | Fast crash recovery; FH + offsets in every call |
| **Idempotent retry** | One client strategy for loss and reboot |
| **Client cache** | Speed vs consistency (close-to-open + attr cache) |
| **Stable WRITE** | Server durability before success |
| **VFS** | Pluggable local + NFS side by side |
