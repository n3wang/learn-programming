# Databases and Streams

> **Adapted from:** Martin Kleppmann, *Designing Data-Intensive Applications* (O'Reilly, 2017), Chapter 11 — rewritten and condensed for teaching.

[Transmitting Event Streams](./transmitting-event-streams) treated messaging and databases as genuinely different tools — but the comparison table in that lesson hinted at something deeper: log-based brokers already borrow real ideas from databases (durability, replayable history), and it turns out the borrowing runs both directions. This lesson runs it the other way — treating a **database write itself** as just another kind of event — and follows that idea through to two genuinely powerful techniques: **change data capture** and **event sourcing**.

---

## Keeping Systems in Sync

Real applications almost never rely on a single storage technology. A typical stack might combine an OLTP database serving live requests, a cache accelerating hot reads, a full-text search index, and a separate data warehouse for analytics — each holding its **own** copy of overlapping data, in its **own** representation, optimized for its **own** purpose. The moment the same underlying data lives in more than one place, those copies have to be kept in sync: update an item in the primary database, and that same update needs to eventually land in the cache, the search index, and the warehouse too.

Batch-oriented **ETL** (already covered in this series' data-warehousing coverage) is one standard answer — periodically re-extracting, transforming, and bulk-loading a fresh copy. When that periodic-batch cadence is too slow, a tempting-looking alternative is **dual writes**: application code explicitly writes to each system directly whenever data changes — first the database, then the search index, maybe the cache invalidation too, sometimes even concurrently.

### The Race Condition Dual Writes Can't Avoid

Dual writes have a genuinely serious, easy-to-miss problem. Picture two clients concurrently updating the same item `X`: client 1 wants to set it to `A`, client 2 wants to set it to `B`. Both clients write to the database *and* the search index — but nothing guarantees those two writes land in the **same relative order** on both systems. Suppose the database happens to process client 1's write first, then client 2's — leaving the database's final value as `B`. But suppose the search index, due to nothing more than ordinary network timing, happens to receive client 2's write **first**, then client 1's — leaving the search index's final value as `A`. Both systems now hold **permanently different, silently inconsistent** values for the same item — with **no error raised anywhere**, and (absent something like the version vectors from [Leaderless Replication](../distributed-data/leaderless-replication#detecting-concurrent-writes)) no way to even *detect* that this happened after the fact. One value simply, silently overwrote what should have been the "true" final value, in each system independently, with no coordination between them.

A second, entirely separate problem with dual writes: one of the two writes can simply **fail** while the other succeeds — a fault-tolerance issue, not a concurrency one, but with the identical end result — two systems now permanently disagree. Making the two writes succeed or fail **together**, atomically, is precisely the **atomic commit problem** already covered in [Distributed Transactions and Two-Phase Commit](../distributed-data/distributed-transactions-and-two-phase-commit) — genuinely solvable, but expensive, and rarely worth the operational cost it demands.

The deeper diagnosis: [Leaders and Followers](../distributed-data/leaders-and-followers) already established that a **single leader** is precisely what determines a consistent write order that every follower can safely replicate — the state-machine-replication principle. In the dual-writes scenario, there effectively **is** no single leader across the two systems — the database might have its own internal leader, the search index its own, separately, with **neither** deferring to the other — which is exactly the structural shape of [Multi-Leader Replication](../distributed-data/multi-leader-replication), and exactly why the identical class of write conflicts shows up here too. Things would be meaningfully better if there really *were* just one true leader — say, the database itself — with the search index behaving as nothing more than its **follower**. The natural next question: can that actually be made to work in practice?

## Change Data Capture

For decades, most databases' internal replication logs were treated as a private implementation detail — never a documented, public API. Applications were expected to interact through the database's own query language, not by reverse-engineering its internal write log — which made it genuinely difficult to reliably pipe a database's changes out to a *different* storage technology like a search index or a cache.

**Change data capture (CDC)** is the practice of observing every write made to a database and extracting it, in order, as a **stream** — ideally delivered essentially immediately, as each write actually happens. The core idea: capture a database's changes once, then continuously apply that **identical, ordered** stream of changes to a search index (or any other derived system). As long as every downstream consumer applies changes in that exact same order, its data stays in sync with the source, by construction — the search index (and any other derived system) is simply another **consumer** of that one shared, authoritative change stream.

### Implementing CDC

Under this framing, the search index and every other derived system are just **derived data systems**, in the precise sense this whole series has used the term — data that is, at its core, just another *view* onto the data already living in the true system of record. Change data capture is the specific mechanism that keeps every one of those views honestly, accurately synchronized with that record. In effect, CDC makes exactly **one** database the leader (the one changes are captured *from*) and turns every other participating system into its **follower** — and a log-based message broker (from [Transmitting Event Streams](./transmitting-event-streams#partitioned-logs-combining-database-durability-with-messagings-low-latency)) is a particularly good fit for actually transporting that change stream, precisely because it preserves ordering, sidestepping the redelivery-reordering problem covered in that same lesson.

Two broad implementation strategies exist: **database triggers** (registering a trigger that observes every table change and appends a corresponding entry to a separate changelog table) — genuinely simple to set up, but historically fragile and carrying real performance overhead — or **directly parsing the database's own replication log** (PostgreSQL's write-ahead log, MySQL's binlog, MongoDB's oplog), a more robust approach at the cost of extra complexity, particularly around handling schema changes gracefully. Real production tools built on the latter approach include Debezium and Maxwell for MySQL, and Bottled Water for PostgreSQL.

Like messaging generally, CDC is normally **asynchronous** — the system of record doesn't block a write waiting for every downstream consumer to catch up. That keeps a slow consumer from dragging down the primary system's own performance, but it directly inherits every one of the [replication-lag problems](../distributed-data/problems-with-replication-lag) already covered earlier in this series.

### The Initial Snapshot Problem

Given the *entire* history of changes ever made to a database, you could, in principle, reconstruct its full current state purely by replaying that log from the very beginning. In practice, though, keeping every change **forever** would demand an unreasonable amount of disk space, and replaying all of it would take an unreasonable amount of time — so change logs get **truncated** eventually. Building a brand-new full-text index, for instance, genuinely needs a **complete** copy of the database — a log of only *recent* changes would be silently missing every item that simply hasn't been touched recently. The practical fix: start from a **consistent snapshot** (the same technique already covered for [setting up new replication followers](../distributed-data/leaders-and-followers#setting-up-new-followers)), explicitly tied to a specific, known position in the change log, so a consumer knows exactly where to resume applying changes once the snapshot itself has been fully loaded.

### Log Compaction: A Genuine Alternative to Repeated Snapshots

Without that full change history retained, spinning up a brand-new derived system means going through the full snapshot dance every single time. **Log compaction** — already covered for hash-index storage engines in [Hash Indexes and LSM-Trees](../designing-data-intensive-applications/hash-indexes-and-lsm-trees#hash-indexes) — offers a genuinely elegant alternative. The underlying principle carries over directly: periodically scan the log for entries sharing the same key, discard everything but the **most recent** update for each one (a special `null`-valued **tombstone** entry marks a deletion, causing that key to be fully dropped during compaction). Disk space needed for a compacted log depends only on the database's **current** contents, never on the total historical volume of writes.

Applied to CDC specifically, this gives you something genuinely powerful: as long as every change carries a primary key, and every update for that key fully replaces the previous one, a compacted log is guaranteed to still hold the **latest** value for **every** key that's ever existed — even after old duplicate updates have long since been garbage-collected. Rebuilding a derived system from scratch, then, is as simple as starting a fresh consumer at offset `0` of the compacted topic and reading straight through — no separate, special-cased snapshot mechanism required at all. Apache Kafka directly supports this feature, which is precisely what lets it double as genuine durable storage, not merely a transient messaging layer.

### First-Class API Support for Change Streams

CDC used to always mean *retrofitting* change extraction onto a database never designed with it in mind — but modern systems increasingly expose change streams as a genuine, first-class, **designed-in** interface: RethinkDB lets a query subscribe directly to notifications when its own results change; Firebase and CouchDB both build data synchronization directly around a native change feed; VoltDB lets a transaction explicitly export tuples into a dedicated, insert-only, non-queryable output stream table. **Kafka Connect** specifically exists to unify CDC support across a wide range of source database systems, feeding that unified change stream directly into Kafka — from which it can update derived systems, or feed straight into the kind of stream-processing systems this series continues on to next.

## Event Sourcing

**Event sourcing** — developed within the domain-driven design community — shares CDC's core instinct (store every change as an immutable log of events) but applies it at a genuinely **different level of abstraction**:

| | Change data capture | Event sourcing |
|---|---|---|
| **Application's own model** | The application freely mutates the database — updating and deleting records directly | The application is explicitly built around immutable events from the start; the event store is append-only, and mutation/deletion is actively discouraged or outright disallowed |
| **Where the log comes from** | Extracted *after the fact*, at a low level (parsing a replication log) — the application doesn't even need to know CDC is happening | The event log **is** the primary source of truth — the application deliberately writes to it directly |
| **What an event records** | A low-level state change (a row updated, a field changed) | A meaningful, application-level occurrence ("student cancelled their enrollment"), deliberately framed at a higher level of intent |

That difference in framing is a genuinely powerful **data modeling** tool in its own right. Recording "student cancelled their course enrollment" as one clear, intent-carrying event is meaningfully more expressive than recording its side effects directly — "one row deleted from `enrollments`, one row added to `feedback`" — since those side effects already bake in a lot of *assumptions* about exactly how the data will end up being used later. Introduce a genuinely new feature down the line — say, "automatically offer the freed-up seat to the next person on the waitlist" — and the event-sourcing model lets that new behavior simply **chain off** the *existing*, already-recorded event, with zero need to retroactively rewrite history. Beyond that expressiveness, event sourcing also tends to make an application meaningfully easier to evolve over time, easier to debug (the full causal history of *why* something happened is right there, explicitly, in the log itself), and more resistant to entire categories of application bugs.

### Deriving Current State From the Event Log

An event log **by itself** isn't directly useful to most users — a shopping-cart user wants to see their **current** cart contents, not a raw, unfiltered, append-only history of every add and remove they've ever performed. Applications built around event sourcing therefore need a **deterministic transformation** that takes the full event log and derives current, presentable application state from it — replaying that same log always has to produce the identical result, every single time.

This has a genuine, important consequence for **log compaction** specifically, and it's where event sourcing and CDC meaningfully diverge: a CDC event typically carries the entire **new** version of a record, so the *current* value for any given key is fully determined by that key's single most recent event alone — compaction can freely discard everything older. Event sourcing's events, by contrast, are deliberately framed at a **higher** level — an "add item to cart" event doesn't, by itself, tell you the cart's full current contents; it only tells you what *changed*. Later events generally don't fully **override** earlier ones the way a CDC update does — reconstructing the true current state genuinely requires the **complete** history, in order, not merely the newest entry per key. Simple key-based log compaction, as a direct consequence, **doesn't** apply the same way here. (Real event-sourced applications typically still take periodic **snapshots** of derived state purely as a performance optimization — to avoid replaying the entire history from scratch on every single read — but conceptually, the underlying assumption remains that the complete raw event history stays available, and could always, in principle, be fully replayed from the beginning if genuinely needed.)

### Commands vs. Events

Event sourcing draws a careful, deliberate line between **commands** and **events**. A request freshly arriving from a user starts life as a **command** — at that point, it can still, genuinely, fail (a chosen username might already be taken; a specific theater seat might already be booked). The application first has to **validate** that the command can actually succeed. Only *after* that validation genuinely passes does it become an **event** — durable, immutable, and, from that moment forward, an unchangeable **fact**.

Picture a user registering a username, or reserving one specific theater seat — precisely the same uniqueness scenario already covered through the lens of consensus in [Fault-Tolerant Consensus](../distributed-data/fault-tolerant-consensus#defining-consensus-precisely). The application first has to confirm the username or seat genuinely isn't already claimed — **only then** does it generate the corresponding event recording that it now has been. Once that event exists, it's permanently, immutably true — even if the customer later cancels the reservation entirely, the historical fact that they *did* hold it for some span of time remains true forever; a cancellation is recorded as a wholly **separate**, later event layered on top, never as a retroactive rewrite of history.

A genuinely important structural rule falls directly out of this: a **consumer** of the event stream is never permitted to reject an event outright — by the time any consumer actually sees it, it's already been durably committed to the log, and quite possibly already seen by other consumers too. That means all real **command** validation has to happen **synchronously**, strictly *before* anything is allowed to become an event — commonly via a genuinely serializable transaction that atomically validates the command and publishes the resulting event together, as one indivisible unit. An alternative pattern also works well here: split a request like a seat reservation into **two** separate events — first a **tentative** reservation, then a **separate confirmation** event once validation genuinely completes — letting that validation step run fully **asynchronously**, using precisely the total-order-broadcast-based linearizable-storage technique already covered in [Ordering Guarantees](../distributed-data/ordering-guarantees#implementing-linearizable-storage-using-total-order-broadcast).

:::important Key takeaways
- **Dual writes** (updating multiple systems directly from application code) are genuinely unsafe — concurrent writes can land in different orders on different systems, silently diverging with no error raised, and partial failures create the exact same divergence through a different door.
- **Change data capture** fixes this by making one database the single leader and turning every other system into its follower — consuming one shared, correctly-ordered change stream instead of racing independent writes against each other.
- **Log compaction**, applied to a CDC stream, lets a compacted log substitute for a full snapshot — reading it end to end always reconstructs the database's complete current state, since only the latest value per key ever survives compaction.
- **Event sourcing** applies the same "log of immutable events" idea at the *application* level rather than the database level — events capture meaningful intent, not just raw side effects — but this same reframing means simple per-key log compaction generally doesn't apply, since reconstructing current state genuinely requires the full ordered history.
- Event sourcing draws a sharp line between **commands** (which can still fail, and must be validated *before* anything is written) and **events** (durable, immutable facts that downstream consumers can never reject) — a distinction that keeps the whole model both simple to reason about and safe to build on.
:::
