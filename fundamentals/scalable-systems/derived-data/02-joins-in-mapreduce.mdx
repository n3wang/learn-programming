# Joins in MapReduce

> **Adapted from:** Martin Kleppmann, *Designing Data-Intensive Applications* (O'Reilly, 2017), Chapter 10 — rewritten and condensed for teaching.

[Batch Processing with Unix and MapReduce](./batch-processing-with-unix-and-mapreduce) established the map/shuffle/reduce pattern in the abstract. This lesson puts it to work on the problem every real dataset eventually runs into: **joins**. [Graph-Like Data Models](../designing-data-intensive-applications/graph-like-data-models) discussed joins from the query-language side; this is where they actually get *implemented*.

MapReduce has no concept of an index — when it's given a set of input files, it reads *all* of them, a full scan every time. For looking up a handful of records, that's absurdly wasteful compared to an index lookup. But for the kind of aggregate, whole-dataset analytics batch jobs exist to do, a full scan across many parallel machines is often perfectly reasonable — and when we say "join" in a batch context, we specifically mean resolving **every** occurrence of some association across the *entire* dataset, not looking up one specific record.

---

## Reduce-Side Joins: Bringing Data Together by Key

### The Motivating Example

Say you have a log of user activity events (clickstream data — just a user ID per event) and a separate user profile database (containing, say, each user's date of birth), and you want to correlate page popularity with age group. The events don't carry full profile data — embedding it in every single event would be wasteful — so you need to **join** the two datasets on user ID.

The naive approach — query the (remote) user database once per activity event — performs terribly: throughput gets capped by network round-trip time, cache effectiveness depends entirely on data distribution, and hammering the database with a flood of parallel queries risks overwhelming it. It also makes the whole batch job **nondeterministic**, since the remote database's contents can change mid-run. The fix: copy the user database into the *same* distributed filesystem as the activity log (typically via an ETL extraction), so the join can run entirely locally, with no network round-trips per record at all.

### Sort-Merge Joins

Run mappers over **both** inputs, each extracting **the same key** — user ID — regardless of which dataset a mapper is reading:

- Mappers over the activity log emit `(userID, activity_event)`.
- Mappers over the user database emit `(userID, date_of_birth)`.

Once the shuffle partitions and sorts by that shared key, every activity event *and* the one profile record sharing a user ID land **adjacent to each other**, in the same reducer call. A common refinement, **secondary sort**, arranges things so the reducer always sees the profile record **first**, followed by that user's activity events in timestamp order — letting the reducer stash the date of birth in a local variable, then simply stream through the events emitting `(url, age)` pairs as it goes, with no memory overhead beyond that single cached record. This whole technique — sort mapper output by key, let matching records merge together in the reducer — is a **sort-merge join**.

### Why This Works: Mappers as Messages

One clean way to see this pattern: mapper output keys act like **destination addresses**. A mapper "sends a message" to a reducer purely by choosing what key to emit — every key-value pair sharing a key is guaranteed delivery to the same reducer call, no matter which mapper produced it or which machine that mapper ran on. This cleanly separates the **physical** problem (get the right data to the right machine — the framework's job) from the **application logic** (what to actually do once it's there — your job) — a separation ordinary database-backed application code, where a query sits deep inside business logic, doesn't get nearly as cleanly.

### GROUP BY Is the Same Pattern

Grouping — SQL's `GROUP BY` — uses the exact same "bring matching keys together" mechanism: set the mapper's output key to whatever you're grouping by, and every record in a group lands at one reducer call together, ready for a `COUNT`, `SUM`, top-*k*, or any other per-group aggregation. **Sessionization** — reconstructing one user's full sequence of actions, e.g., to compare an old vs. new site design (A/B testing) — is exactly this same grouping pattern, using a session ID or user ID as the key, even when the underlying events are scattered across many different web servers' individual log files.

### Handling Skew

The "bring everything for a key to one place" trick breaks down hard when one key dominates — a celebrity account with millions of followers, say (a **hot key** or **linchpin object**). Routing every event tied to that key to a single reducer creates a genuine **hot spot**: since a MapReduce job only finishes once every reducer finishes, the whole job now waits on that one overloaded reducer. Real mitigations:

- **Pig's skewed join**: sample the data first to detect hot keys, then route *that specific key's* records to a **randomly** chosen reducer (instead of the usual deterministic hash) — spreading one key's load across several reducers, at the cost of needing to replicate the *other* join input for that key to every reducer that might need it.
- **Hive's skewed join optimization**: require hot keys to be declared explicitly in table metadata, store their records separately, and handle just those keys with a map-side join (covered next).
- **Two-stage grouping**: for pure aggregation (not joins), send a hot key's records to a random reducer first for **partial** aggregation, then combine those partial results in a *second* MapReduce pass into the final per-key total.

## Map-Side Joins: Skipping the Shuffle Entirely

Reduce-side joins make no assumptions about the input — but all that sorting, network copying, and merging is genuinely expensive, sometimes forcing data to be written to disk multiple times as it moves through MapReduce's stages. If you *can* make assumptions about your inputs' size, partitioning, or sort order, a **map-side join** skips the reduce stage — and the shuffle — entirely: no reducers, no sorting, each mapper just reads one input block and writes one output file, done.

### Broadcast Hash Joins

If one side of the join is small enough to fit entirely in memory (the user database, say), skip partitioning it at all: **every** mapper loads the *whole* small dataset into an in-memory hash table on startup, then simply streams through its own slice of the large dataset, doing an in-memory hash lookup per record. The name reflects both halves of the mechanism: **broadcast**, because the small input is effectively replicated ("broadcast") to every mapper processing the large input, and **hash**, because of the in-memory lookup structure. (A close variant swaps the in-memory hash table for a read-only on-disk index instead — the OS page cache keeps hot parts of it effectively memory-speed, without requiring the whole dataset to fit in RAM.)

### Partitioned Hash Joins

If **both** join inputs happen to already be partitioned the same way — same key, same hash function, same partition count (say, both split by the last digit of user ID) — the hash-join trick can run **per partition independently**: mapper 3 loads only partition 3 of the small input into its hash table, then scans only partition 3 of the large input. Each mapper's hash table shrinks to a fraction of the full small dataset — a real win, but one that only applies when a prior MapReduce job already produced both inputs in matching, compatible partitions.

### Map-Side Merge Joins

If both inputs are **not only** identically partitioned but **also already sorted** by the join key, memory size stops mattering entirely — a mapper can perform the exact same incremental, ascending-key merge a reducer would, without ever needing either input to fit in memory. This is really the sort-merge join's core merge logic, just relocated to run in the map phase because the sorting work was already done by an earlier job.

### Map-Side Joins Change Downstream Structure

A subtle but important consequence for chained workflows: a **reduce-side** join's output ends up partitioned and sorted by the *join key* — but a **map-side** join's output stays partitioned and sorted exactly like its large input was, since one map task runs per block of that large input regardless of join strategy. Any *downstream* job consuming that output has to know this — which means knowing about a dataset's physical partitioning and sort order, not just its file format, becomes genuinely important metadata (in the Hadoop ecosystem, typically tracked in HCatalog / the Hive metastore).

:::important Key takeaways
- A batch-context "join" means resolving **every** occurrence of an association across a whole dataset — a full scan, not an index lookup — which is exactly why copying data locally beats querying a live remote database per record.
- **Reduce-side (sort-merge) joins** make no assumptions about input structure: mappers extract a shared key from both sides, the shuffle brings matching keys together, and the reducer merges them — the same mechanism underlies both joins and `GROUP BY`.
- **Skewed (hot) keys** bottleneck an entire job, since completion waits on the slowest reducer — sampling-based random routing, explicit hot-key handling, and two-stage aggregation are the standard mitigations.
- **Map-side joins** (broadcast, partitioned, or merge) skip the shuffle entirely by exploiting known properties of the input — small size, matching partitioning, or matching sort order — trading input assumptions for real performance, at the cost of the output inheriting the large input's layout instead of being reorganized by join key.
:::
