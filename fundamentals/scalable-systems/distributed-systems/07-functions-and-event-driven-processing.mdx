# Functions and Event-Driven Processing

> **Adapted from:** Brendan Burns, *Designing Distributed Systems* (O'Reilly), Chapter 9 — rewritten and condensed for teaching.

Earlier lessons assumed **long-running** servers always ready for traffic — right for heavy load, large in-memory state, or background work. Another class of apps only needs to exist **briefly** for a request or **react** to an event. Public clouds productized that style as **function-as-a-service (FaaS)**; similar runtimes also sit on cluster orchestrators in private clouds. FaaS is often **one piece** of a larger design, not the whole system.

:::note Serverless ≠ event-driven
**Serverless** means you do not manage the servers. **Event-driven FaaS** means code runs in response to discrete events. They overlap but are not the same:

| | Serverless | Event-driven |
|---|---|---|
| Multitenant container platform (CaaS) | ✓ | not necessarily |
| Open-source FaaS on machines you own | not really | ✓ |
| Cloud Lambda / Cloud Functions style | often both | ✓ |

Pick **event-driven**, **serverless**, or **both** based on the problem — not the buzzword.
:::

---

## When FaaS Makes Sense

FaaS is a strong tool in a **narrow** context. Stretching it into every service produces brittle, hard-to-operate designs.

### Benefits (mostly for developers)

- Short path from **source → running code** (little packaging ceremony).
- **Automatic scale-out** when traffic rises; failed instances restart elsewhere.
- Functions are **stateless building blocks** — systems tend to stay modular (network is the only integration path; state lives in storage services).

### Challenges

Forced decoupling cuts both ways:

- Hard to see the **whole service**, how functions wire together, and **why** something failed.
- Easy to create accidental **infinite call loops** (`A → B → C → A`) until timeouts burn money — each function is independent, so dependency graphs are not obvious in the code.
- You need **monitoring and alerting** early; that ops cost offsets some of FaaS’s deploy simplicity.

### When FaaS is a poor fit

| Need | Why FaaS struggles |
|---|---|
| **Long background work** (transcode, compress logs) | Time-bounded, event-triggered runs; scheduled pings help alarms, not generic batch jobs |
| **Large data in memory** (search indexes) | Cold start must load state while the user waits; if load stays high enough to keep functions warm, you may be **overpaying** vs a long-running service |
| **Sustained high RPS** | Pay-per-request grows ~linearly; VM/container pricing + reservations often wins once CPUs stay busy |

A common evolution: start on managed FaaS, later run **open-source FaaS on Kubernetes** (or move hot paths to long-running services) to keep the programming model while changing the cost model.

## Pattern: Decorator (Request / Response Transformation)

FaaS shines at **small, stateless transforms** between a client and another service — validate, default fields, enrich headers — then forward. That is the **decorator** idea (similar to Python decorators): wrap an existing API without stuffing the logic into the core handler.

```mermaid
flowchart LR
  CLIENT[Client]
  DEC[Decorator function]
  API[Core API service]
  CLIENT --> DEC
  DEC -->|transformed request| API
  API --> DEC
  DEC --> CLIENT
```

Why FaaS instead of an always-on adapter container?

- Defaulting/validation is often **cheap** — you may not want it scaled 1:1 with a heavy API.
- Easy to **experiment** with transforms, then pull winners into the main service later.

## Pattern: Handling Events

**Requests** usually sit in a longer session (pages, API conversations). **Events** are often one-shot and asynchronous: user signed up, file uploaded, machine rebooting. Variable rates and independence make events a natural FaaS workload — often **beside** a main app server.

Example: **two-factor authentication**. After password success, fire a webhook to a function that generates a code, registers it with the login service, and texts the user — so the login page is not blocked on SMS latency.

## Pattern: Event-Based Pipelines

Some flows look like **flowcharts**: a directed graph of webhooks/functions, edges as HTTP (or other) calls, little shared memory beyond a **context** id in storage.

Vs **microservices**:

- Pipeline steps are **event-triggered** and often short-lived; microservices are usually **long-running**.
- Pipelines easily mix **human** steps (approve a ticket) with automation.

Example CI-ish flow: commit → build → on success open approval ticket → on close push to prod; on failure file a bug and stop.

### Hands On: New user signup pipeline

Orchestrate **required** handlers (always) and **optional** handlers (only if a flag/key is present on the signup payload).

<CodeExercise
  id="dds-faas-signup-pipeline"
  title="Signup pipeline: required vs optional"
  heading="exercise-signup-pipeline"
  lang="python"
  filename="main.py"
  prompt={`(1) Implement create_user(payload, required, optional, call_fn):

(2) For every (key, webhook) in required.items(), call call_fn(webhook, payload).

(3) For every (key, webhook) in optional.items(), call call_fn only if payload.get(key) is not None.

(4) Return the list of webhooks that were actually invoked, in call order.`}
  sampleLog={`(no input)
['https://welcome', 'https://subscribe']
['https://welcome']`}
  starter={`def create_user(payload, required, optional, call_fn):
    # Invoke required always; optional only when payload has that key set.
    # Return list of webhook URLs that were called, in order.
    pass

calls = []

def record(webhook, data):
    calls.append(webhook)

required = {"welcome": "https://welcome"}
optional = {"subscribe": "https://subscribe"}

print(create_user(
    {"username": "ada", "subscribe": True},
    required,
    optional,
    record,
))
calls.clear()
print(create_user(
    {"username": "bob"},
    required,
    optional,
    record,
))
`}
  hint="Loop required.values() (or items) and call; for optional, if payload.get(key) is not None: call. Append each webhook to a list you return."
  solution={`def create_user(payload, required, optional, call_fn):
    invoked = []
    for key, webhook in required.items():
        call_fn(webhook, payload)
        invoked.append(webhook)
    for key, webhook in optional.items():
        if payload.get(key, None) is not None:
            call_fn(webhook, payload)
            invoked.append(webhook)
    return invoked

calls = []

def record(webhook, data):
    calls.append(webhook)

required = {"welcome": "https://welcome"}
optional = {"subscribe": "https://subscribe"}

print(create_user(
    {"username": "ada", "subscribe": True},
    required,
    optional,
    record,
))
calls.clear()
print(create_user(
    {"username": "bob"},
    required,
    optional,
    record,
))
`}
  sourceChecks={[
    {
      name: 'iterates required',
      pattern: 'for\\s+.*\\s+in\\s+required',
      must: true,
      hint: 'loop over required handlers',
    },
    {
      name: 'gates optional on payload',
      pattern: 'payload\\.get\\s*\\(',
      must: true,
      hint: 'use payload.get(key) for optional steps',
    },
    {
      name: 'calls call_fn',
      pattern: 'call_fn\\s*\\(',
      must: true,
      hint: 'invoke call_fn(webhook, payload)',
    },
  ]}
  tests={[
    {
      name: 'required always; optional when present',
      stdin: '',
      equals: "['https://welcome', 'https://subscribe']\n['https://welcome']",
    },
  ]}
/>

Factored this way, each step stays a few lines focused on one job; the **pipeline** (required vs optional webhook lists) is what you reason about at a high level.

:::important Key takeaways
- **FaaS / event-driven** code runs for discrete events; **serverless** is about ops ownership — do not conflate them.
- Great for **stateless transforms**, **async side effects**, and **pipelines** of small handlers; weak for **long jobs**, **huge warm state**, and **always-on heavy RPS** without a pricing rethink.
- Decoupling improves modularity but demands **observability** (watch for cycles and silent failures).
- **Decorator**, **event handler**, and **event pipeline** are three practical ways to drop FaaS beside (not instead of) core services.
- Ideal designs often **compose** FaaS with long-running platforms (e.g. Kubernetes) as the system grows.
:::
