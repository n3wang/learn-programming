# Introduction to Concurrent Programming

> **Adapted from:** Jason Gregory, *Game Engine Architecture*, 3rd ed. (CRC Press, 2018), Chapter 4, Section 4.5 — rewritten and condensed for teaching.

[Explicit parallelism](./explicit-parallelism) gives us hardware that can run more than one instruction stream at once, and [Operating System Fundamentals](./operating-system-fundamentals) gave us the processes and threads the OS schedules onto that hardware — but *using* threads correctly to solve a problem together is a separate skill: **concurrent programming**. Rob Pike (Distinguished Engineer at Google, and a designer of Go) defines concurrency as "the composition of independently executing computations." That phrasing matters: the flows of control in a concurrent program run semi-independently, but they're *composed* — they share data and synchronize with each other to solve one problem together.

Concurrency shows up in more places than "multithreaded code": a piped shell command (`cat render.cpp | grep "light"`), a single process with many threads sharing memory, a GPU's thousands of cooperating threads rendering a frame, or a multiplayer game synchronizing state across machines over a network are all concurrent systems.

### Why Write Concurrent Software?

Two distinct motivations show up in practice, and it's worth telling them apart:

1. **The problem is naturally concurrent.** Modeling it as multiple semi-independent flows of control is simply the more natural fit — a chat server handling many client connections, for instance.
2. **The hardware rewards it.** A problem that's perfectly sequential in nature might still be restructured concurrently purely to spread the work across a multicore machine and finish faster.

## Concurrent Programming Models

Cooperating threads need to communicate — sharing data and synchronizing activity. There are two fundamental ways to do that:

- **Message passing** — threads exchange explicit messages (over a network, through a pipe, via an in-memory queue) to share data and coordinate. Works whether the threads live in one process, in separate processes on one machine, or on entirely separate machines.
- **Shared memory** — two or more threads are simply given access to the *same* physical memory and operate directly on the objects living there. This only works when every participant runs on one machine with RAM every core can actually see. Threads within a single process get this for free (they already share a virtual address space); separate processes can opt in by mapping the same physical pages into each of their address spaces.

Neither model is exclusive to the other underneath the hood — **distributed shared memory** fakes shared memory on top of message passing across machines, and a message queue living in shared memory implements message passing on top of shared memory. They're two views of the same coordination problem.

Shared memory is the more *efficient* choice for large data, since nothing needs to be copied for transmission — but that efficiency comes at a cost: sharing anything, memory included, opens the door to the synchronization bugs this lesson (and the next two) are all about. Message passing doesn't eliminate that risk, but it tends to reduce its blast radius. Game engines are typically single-process, multithreaded programs, which is exactly why this series — like the book it's adapted from — focuses on shared-memory concurrency; the exception is networked multiplayer, which leans heavily on message passing instead. Once shared-memory concurrency clicks, message passing is comparatively easy to pick up.

## Race Conditions

A **race condition** is any situation where a program's behavior depends on timing — the outcome can change if the relative speed or ordering of events elsewhere in the system changes. Not every race condition is a bug: a **critical race** is specifically a race condition capable of producing *incorrect* behavior.

Bugs caused by critical races have a well-earned reputation for feeling "impossible": intermittent crashes, occasionally-wrong results, data structures that end up corrupted, bugs that vanish in a debug build, bugs that disappear for days and then reappear (traditionally the night before a trade-show demo), bugs that vanish the moment you add logging to hunt for them. Programmers call these **Heisenbugs** — the act of observing the system changes its timing enough to change its behavior.

### Data Races

A **data race** is a critical race where two or more flows of control interfere with each other while reading and/or writing *shared* data, corrupting it. This is the central problem concurrent programming exists to solve — every concurrency technique in this series ultimately boils down to eliminating data races, either by tightly controlling access to shared data, or by giving each thread its own private copy (turning a concurrency problem back into a sequential one).

Consider this innocent-looking C/C++ snippet:

```cpp
int g_count = 0;

inline void IncrementCount() {
    ++g_count;
}
```

On x86, `++g_count` typically compiles to three separate machine instructions — a classic **read-modify-write (RMW)** sequence:

```asm
mov  eax, [g_count]   ; read g_count into EAX
inc  eax              ; modify: increment the value
mov  [g_count], eax   ; write EAX back into g_count
```

If two threads, A and B, each call `IncrementCount()` exactly once, we'd expect `g_count` to end up at `2` — whichever thread goes first, the other sees its result and adds one more:

| Step | Thread A | Thread B | `g_count` |
|---|---|---|---|
| 1 | reads 0 | | 0 |
| 2 | increments (local = 1) | | 0 |
| 3 | writes 1 | | 1 |
| 4 | | reads 1 | 1 |
| 5 | | increments (local = 2) | 1 |
| 6 | | writes 2 | **2** ✓ |

But if the two threads' RMW sequences **interleave** — A gets preempted right after its `mov` (read) but before its `inc`, and B runs its own read in the gap — both threads end up incrementing from the *same* starting value:

| Step | Thread A | Thread B | `g_count` |
|---|---|---|---|
| 1 | reads 0 | | 0 |
| 2 | *(preempted)* | reads 0 | 0 |
| 3 | | increments (local = 1) | 0 |
| 4 | | writes 1 | 1 |
| 5 | increments (local = 1) | | 1 |
| 6 | writes 1 | | **1** ✗ |

Two increments, and `g_count` ends up at `1` instead of `2` — one update was silently lost. This exact failure mode can happen on a single core via preemptive context-switching (as shown above), *or* on separate cores running genuinely in parallel, if the two RMW sequences happen to overlap in time (offset from each other, or even in perfect lockstep) — either way, both threads can load the same stale value before either writes its result back.

:::tip Activity: simulate the race yourself
Since a hosted sandbox can't reliably reproduce real thread scheduling on demand, the exercise below has you *play* the scheduler — manually reproducing the exact interleaving from the second table above using plain, deterministic function calls. If you can make `g_count` come out as `1` instead of `2` on purpose, you've proven to yourself precisely how the bug happens.
:::

## Critical Operations and Atomicity

Not every interruption is dangerous. If a thread operates on data no other thread can see, it can be interrupted at any point with zero consequence. Likewise, an operation on object X can't meaningfully interfere with an operation on an unrelated object Y. Data races only happen when an operation on a *shared* object is interrupted by *another operation on that same object* — so it only makes sense to talk about a race in relation to one particular shared object. Call any operation capable of reading or mutating that object a **critical operation**. If we can guarantee that a shared object's critical operations never interrupt one another, the object is safe — and an operation with that guarantee is called **atomic** (it has the property of **atomicity**).

### Invocation and Response

Early on, most of us are taught that an algorithm's correctness only depends on the *order* of its steps, not how long each step takes. That model breaks down the moment multiple threads are involved, because operations now have a real, nonzero duration, and "before/after" between two multi-step operations running on different threads stops being well-defined.

The fix is to stop reasoning about operations and start reasoning about **instantaneous events**. Any operation, however long it takes, can be split into two such events: its **invocation** (the instant it begins) and its **response** (the instant it's considered complete). Given any two instantaneous events, exactly one relationship holds: one happens before the other, or they're simultaneous (rare, but possible on hardware with a synchronized clock across cores).

This lets us cut any code containing a critical operation into three pieces, in **program order** (the order things appear in source):

- **Preamble** — everything before the critical operation's invocation.
- **Critical section** — the critical operation itself.
- **Postamble** — everything after the critical operation's response.

### Defining Atomicity Precisely

An "interruption" now has a precise meaning: one operation's invocation and/or response falls *between* another operation's invocation and response. Putting it together:

:::important Atomicity, defined
A critical operation executes **atomically** if its invocation and response are not interrupted by another critical operation on the *same* shared object.
:::

Crucially, a critical operation can be interrupted all day long by *unrelated* operations (on other objects, or non-critical code) without any problem — atomicity is only violated when two critical operations *on the same object* overlap. The cleanest way to think about a guaranteed-atomic operation: from every other thread's point of view, it appears to happen **instantaneously** — as if invocation and response were the same event — so nothing else can ever "sneak in" during it.

### Making an Operation Atomic: The Mutex

The most common tool for forcing atomicity is a **mutex** — an OS-provided object that behaves like a padlock a thread can lock and unlock. Guard a critical operation's invocation with acquiring the mutex, and its response with releasing it. Since the OS guarantees only one thread can hold a given mutex lock at a time, no other critical operation on that object can ever have its invocation or response land inside the locked region — exactly the guarantee atomicity requires. (Mutexes are one of several **thread synchronization primitives** the OS provides — the full toolkit is the subject of [Thread Synchronization Primitives](./thread-synchronization-primitives).)

### Atomicity as Serialization

Without atomicity, a group of threads all performing the same operation on shared data can overlap in essentially any order, at any time — an unpredictable jumble. Wrapping the operation in a mutex lock doesn't let you *choose* the order threads run in, but it does guarantee that only one thread is ever inside the operation at once — which transforms that jumble into *some* well-defined sequential order. This transformation — concurrent, overlapping access becoming one-at-a-time, sequential access — is called **serialization**, and it's the core mechanism nearly every concurrency tool in this series relies on.

:::note A term worth knowing
A shared data store that guarantees atomicity this way is called **linearizable** — one specific, well-studied point in a broader family of **data-centric consistency models** (contracts between a shared data store and the threads using it). This is a deep topic in its own right; search "consistency model" and "linearizability" if you want to go further than this series does.
:::

:::important Key takeaways
- **Concurrency** is Pike's "composition of independently executing computations" — flows of control that run semi-independently but coordinate via shared data and synchronization.
- **Message passing** and **shared memory** are the two fundamental ways concurrent threads communicate; shared memory is more efficient for large data but is exactly what makes data races possible, which is why game engines (single-process, multithreaded) live and die by getting shared-memory concurrency right.
- A **data race** happens when a read-modify-write sequence on shared data isn't protected, letting two threads read the same stale value and silently lose one of their updates — this can happen via preemption on one core *or* genuine overlap across cores.
- An operation is **atomic** if its invocation and response can never be interrupted by another critical operation on the same shared object — practically achieved by wrapping it in a **mutex**, which **serializes** access into some well-defined one-at-a-time order.
:::
