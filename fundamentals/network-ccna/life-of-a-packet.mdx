# The Life of a Packet

The dest **IP** is written once, at the sender, and it stays **PC3** the whole way. At every hop the packet is stuffed into a **new Ethernet frame** whose dest **MAC** is only the **next box**. Layer 3 is end-to-end. Layer 2 is hop-to-hop.

## The campus in one picture

Four prefixes, three routers, two access switches:

```text
PC1 .11          R1               R2               R3          PC3 .11
PC2 .12 — SW1 — G0/1 .1           |                G0/1 .1 — SW2 — PC4 .12
                G0/0 .1 ——— .2 G0/0             G0/0 .2
                     192.168.12.0/24   192.168.23.0/24
     192.168.1.0/24                                    192.168.3.0/24
```

<LessonFigure src="/img/ccna/fig-10-1.png" alt="The whole trip at a glance: what PC1, the switches, and each router do." caption="Figure 10.1 — The whole trip at a glance: what PC1, the switches, and each router do." maxWidth={640} />

PC1 pings **192.168.3.11**. The packet type could be anything; ICMP echo is just easy to name. What matters is the path.

## PC1 to R1 — leave the LAN

PC1 is `192.168.1.11/24`. Its local range is `192.168.1.0`–`192.168.1.255`. `192.168.3.11` is **not** in that range, so PC1 will not ARP for PC3. The two hosts do not share a Layer 2 domain. PC1 sends to its **default gateway** — here `192.168.1.1` on R1 G0/1 (often learned later via DHCP).

It still needs a dest **MAC**. That is **ARP**:

1. ARP **request** (broadcast dest `ffff.ffff.ffff`): who-has `192.168.1.1`?
2. SW1 **learns** PC1’s MAC on the ingress port and **floods** the broadcast.
3. PC2 hears it and **drops** — the target IP is not `.12`.
4. R1 **replies unicast**, and **also** writes PC1 into its own ARP table. ARP is two-way learning.
5. SW1 learns R1 G0/1 and **forwards** the known unicast to PC1.
6. PC1 stores `192.168.1.1 → R1 G0/1 MAC`.

Now the echo request can leave: dest IP **PC3**, dest MAC **R1 G0/1**. SW1 already has that MAC, so this frame is a thin known-unicast path.

<LessonFigure src="/img/ccna/fig-10-2.png" alt="PC1 ARPs for its default gateway, R1 G0/1; SW1 floods the request and learns MACs." caption="Figure 10.2 — PC1 ARPs for its default gateway, R1 G0/1; SW1 floods the request and learns MACs." maxWidth={600} />

Two tables, two jobs:

- **MAC address table** (switch): MAC → **port**. Forward or flood frames. The switch does not rewrite the frame.
- **ARP table** (host or router): IP → **MAC**. Build the next Ethernet header.

## R1 to R2 — look up, then a new frame

R1’s dest MAC is its own, so it **de-encapsulates** and reads the IPv4 header. Dest IP is still `192.168.3.11`. It walks the **routing table** and picks the **most specific matching route** — the match with the **longest prefix**.

Simplified R1 table:

| Route | Kind | Out |
| --- | --- | --- |
| 192.168.1.0/24 | connected (C) | G0/1 |
| 192.168.1.1/32 | local (L) | G0/1 |
| 192.168.12.0/24 | connected | G0/0 |
| 192.168.3.0/24 | static (S) | via 192.168.12.2, G0/0 |

`192.168.3.11` matches only the static `/24`. Next hop is **192.168.12.2** (R2 G0/0). R1 knows that IP, not the MAC, so it ARPs on the `192.168.12.0/24` link. No switch sits between R1 and R2 — the broadcast still goes out, but only R2 is there to hear it. Both routers add ARP rows. R1 builds a **new** frame: src R1 G0/0, dest R2 G0/0, same IPv4 header inside.

<LessonFigure src="/img/ccna/fig-10-3.png" alt="R1: route lookup to 192.168.3.0/24 via R2, then ARP for R2’s MAC before forwarding." caption="Figure 10.3 — R1: route lookup to 192.168.3.0/24 via R2, then ARP for R2’s MAC before forwarding." maxWidth={600} />

How that static row got into the table is a later chapter. For this walk you only need: **longest match wins**, then **ARP the next hop**.

## R2 to R3 — same movie, next reel

R2 de-encapsulates. Longest match is `S 192.168.3.0/24` via `192.168.23.2` out G0/1. ARP for R3 G0/0. New frame. Dest IP still PC3.

<LessonFigure src="/img/ccna/fig-10-4.png" alt="R2: the same steps toward R3 — route lookup, ARP for the next hop, new frame." caption="Figure 10.4 — R2: the same steps toward R3 — route lookup, ARP for the next hop, new frame." maxWidth={600} />

## R3 to PC3 — connected means “this LAN”

R3’s longest match is **connected** `192.168.3.0/24` on G0/1. There is no further router. The next MAC is **PC3 itself**. R3 ARPs for `192.168.3.11`. SW2 floods. PC4 drops. PC3 replies. SW2 learns both MACs. R3 forwards the echo as a known unicast.

<LessonFigure src="/img/ccna/fig-10-5.png" alt="R3: the destination is on a connected LAN, so it ARPs for PC3 itself and delivers." caption="Figure 10.5 — R3: the destination is on a connected LAN, so it ARPs for PC3 itself and delivers." maxWidth={600} />

PC3 has the packet. For ping, it now builds an **ICMP echo reply** to `192.168.1.11`.

## PC3 back to PC1 — same rules, warm tables

The return trip uses the same ideas: dest IP is remote → frame to **R3** (PC3’s gateway) → each router longest-matches toward `192.168.1.0/24` → last hop R1 ARPs… except it **already has** PC1, and the switches **already have** the MACs.

<LessonFigure src="/img/ccna/fig-10-6.png" alt="PC3’s reply to PC1: every ARP table is already warm, so no ARP this time." caption="Figure 10.6 — PC3’s reply to PC1: every ARP table is already warm, so no ARP this time." maxWidth={640} />

So you see four frames, IPs swapped, MACs changing each hop, and **no** ARP request, **no** flood. That is not a special “reply protocol.” It is the same forwarding with caches already filled.

```text
PC3 → R3 G0/1     src IP .3.11  dest IP .1.11   dest MAC = gateway
R3  → R2 G0/1     same IPs                      dest MAC = R2
R2  → R1 G0/0     same IPs                      dest MAC = R1
R1  → PC1         same IPs                      dest MAC = PC1
```

## What to keep

- Off-LAN: host ARPs the **gateway**, never the remote dest.
- Switch: learn source, flood broadcast / unknown unicast, forward known unicast. Frames are not rewritten.
- Router: dest MAC is me → de-encap → **longest prefix match** → ARP next hop (or dest host if connected) → **new** frame.
- Packet dest IP is constant. Frame dest MAC is the next hop only.
- A second packet on a warm path skips ARP and flood.
