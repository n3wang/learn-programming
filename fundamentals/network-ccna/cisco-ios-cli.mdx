# The Cisco IOS CLI

Exam language splits in two. Some topics say *explain* or *identify* — you need the idea. Many others say **configure** or **configure and verify** — you need the idea **and** the commands. This chapter is the shared floor under every later “type this on the box” topic. We will touch local passwords (`enable` / `enable secret`) as a first real change. Telnet, SSH, and the wireless LAN controller GUI wait for later.

Routers and switches in this track both run **Cisco IOS**. The commands here work on both.

## Two kinds of shell

A **shell** is the outer face of an operating system: the program you use to talk to the machine.

A **GUI** is windows, menus, a pointer. You already live in one on a PC or a phone. The CCNA still expects one Cisco GUI later: the **wireless LAN controller (WLC)** in a browser. Not this chapter.

<LessonFigure src="/img/ccna/fig-5-1.png" alt="A wireless LAN controller managed through its web GUI in a browser." caption="Figure 5.1 — A wireless LAN controller managed through its web GUI in a browser." maxWidth={560} />

A **CLI** is text. You type a line, press Enter, the device answers. Windows Command Prompt is a cousin. Cisco IOS is the CLI this exam lives in. It looks sharp the first week and becomes muscle memory if you type, not only read. Packet Tracer (or a real box) is the right homework.

<LessonFigure src="/img/ccna/fig-5-2.png" alt="A Windows Command Prompt: a CLI running inside the GUI." caption="Figure 5.2 — A Windows Command Prompt: a CLI running inside the GUI." maxWidth={480} />

## How you reach the CLI

Two doors:

- A **console** cable into the device’s **console port** — you must be in the room. The cable is short. The port is **not** a network interface; it cannot carry user traffic.
- **Telnet** or **SSH** across the network — later.

Many chassis offer both a **USB Mini-B** console and an **RJ45** console. Use one at a time.

<LessonFigure src="/img/ccna/fig-5-3.png" alt="Two console ports on a Cisco switch: USB Mini-B and RJ45." caption="Figure 5.3 — Two console ports on a Cisco switch: USB Mini-B and RJ45." maxWidth={420} />

USB console is often just a USB cable with the right ends. RJ45 console wants a **rollover** cable, not the straight-through or crossover from the cables chapter. Rollover is pin 1 to 8, 2 to 7, 3 to 6, 4 to 5, and the mirror back.

<LessonFigure src="/img/ccna/fig-5-4.png" alt="Rollover cable wiring: pin 1 meets pin 8, pin 2 meets pin 7, and so on." caption="Figure 5.4 — Rollover cable wiring: pin 1 meets pin 8, pin 2 meets pin 7, and so on." maxWidth={480} />

Then you need a **terminal emulator** (PuTTY is a common free one on Windows). Typical Cisco console serial settings, when you have hardware: **9600** baud, **8** data bits, **1** stop bit, **parity none**, **flow control none**. The exam will not grade your PuTTY clicks. In Packet Tracer you click the icon and you are on the CLI.

<LessonFigure src="/img/ccna/fig-5-5.png" alt="PuTTY set up for a serial console: 9600 baud, 8 data bits, 1 stop bit, no parity, no flow control." caption="Figure 5.5 — PuTTY set up for a serial console: 9600 baud, 8 data bits, 1 stop bit, no parity, no flow control." maxWidth={420} />

## Modes: the prompt is the map

A brand-new box may offer a **system configuration dialog**. Decline it (`no`). You do not need that wizard.

You land in **user EXEC**. The prompt is `hostname>` — default hostname `Router` on a router:

```text
Router>
```

User EXEC can look, a little. `show clock` is fine. It cannot change the config, and it cannot `reload` the box. Intrusive verbs fail with a `%` message from IOS.

**Privileged EXEC** is the next rung. `enable` (or `en` if that prefix is unique). The `>` becomes `#`:

```text
Router> enable
Router#
```

Now `show` is complete, and operational verbs work: **reload**, save, move files. `disable` goes back to user EXEC. Almost nobody bothers; privileged can already do everything user can.

Neither EXEC mode **edits** the configuration. For that, from privileged EXEC:

```text
Router# configure terminal
Router(config)#
```

**Global configuration** is the first config mode. Later chapters add interface config and others; you reach those from here. `hostname R1` takes effect **immediately**. The prompt becomes `R1(config)#`. In a lab we use `R1`, `SW1`. In a building, people often bake in a site name.

`no` undoes a line: `no hostname R1` returns the default `Router`.

<LessonFigure src="/img/ccna/fig-5-6.png" alt="Moving between user EXEC, privileged EXEC, and global configuration mode." caption="Figure 5.6 — Moving between user EXEC, privileged EXEC, and global configuration mode." maxWidth={560} />

Back to privileged EXEC: `end`, `exit` (from global config), **Ctrl-C**, or **Ctrl-Z**. From a *nested* config mode, `exit` climbs one step to global config; `end` / Ctrl-C / Ctrl-Z jump all the way to privileged. Careful with **Ctrl-Z**: if you are mid-line it behaves like Enter, then `end`. **Ctrl-C** just aborts.

`show` does not run in config modes. Prefix it with **`do`**: `do show clock` keeps you in `(config)#`.

```text
user EXEC          Router>
       enable ↓  ↑ disable
privileged EXEC    Router#
  configure terminal ↓  ↑ end / exit / Ctrl-C / Ctrl-Z
global config      Router(config)#
```

## Keys and context-sensitive help

While a line is still being edited:

- Arrows move the cursor; **Ctrl-A** start of line, **Ctrl-E** end, **Ctrl-U** delete left of the cursor.
- **Up** / **Down** walk the command history.

**Context-sensitive help** — the question mark, no Enter needed:

| You type | IOS shows |
| --- | --- |
| `?` | commands legal in *this* mode |
| `show ?` | keywords that may follow `show` |
| `en?` | commands that start with `en` |
| `en` then **Tab** | completes to `enable` if that is the only match |
| `en` then **Enter** | runs `enable` if unique; `e` Enter is “ambiguous command” |

`<cr>` in a `?` list means Enter is legal now. A pipe (`|`) filters `show` output — we will use `| include` in a moment.

`conf t` is enough for `configure terminal`. Practice the short forms until they are boring.

## Two config files

IOS keeps **two** text files.

**running-config** lives in **RAM**. It is what the box is doing *now*. Every config command edits it and takes effect at once. RAM dies on power-off or **reload**.

**startup-config** lives in **NVRAM** (non-volatile). It does not run the box until boot. At boot, IOS **copies startup-config into RAM**. No startup-config file means **factory-default** (the device as it left the factory).

Save, from privileged EXEC — all three do the same copy, RAM → NVRAM:

- `write`
- `write memory`
- `copy running-config startup-config`

A first boot has no startup-config until you save once.

Wipe NVRAM (`write erase`, `erase nvram:`, or `erase startup-config`) and **reload** to get factory-default again.

`show running-config` and `show startup-config` print the files. Long output pauses at `--More--`: Enter for one line, space for a screen.

## Locking privileged EXEC

Privileged EXEC is the door to `configure terminal`. Give it a password.

**`enable password`** (global config) is the old door. Case-sensitive. After it exists, `enable` asks `Password:` and hides what you type. The problem: the word sits in running-config in **cleartext**. Anyone who can `show run` can read it.

`service password-encryption` turns current and future passwords into **type 7** ciphertext. Type 7 is weak — it stops a shoulder, not a serious reader. `no service password-encryption` does not unwrap passwords already stored; it only stops encrypting new ones.

**`enable secret`** is the door you should actually use. It stores a **hash** (one-way), not reversible type 7. `enable secret cisco` (or whatever word). If **both** password and secret are configured, **only the secret works**. The `enable password` line can remain in the file and still not let anyone in.

The hash type depends on the IOS train. **Type 9** (scrypt) is stronger than **type 5** (MD5). Prefer 9 when the box offers it. Picking an algorithm by hand is a later chapter.

```text
R1(config)# enable secret lab
R1# show running-config | include enable
```

The pipe keeps only lines that contain `enable`.

## How to make a change that survives reboot

1. Console in (rollover or USB). Decline the wizard.
2. `enable` → privileged EXEC (`#`).
3. `configure terminal` → `(config)#`.
4. Type the change (`hostname R1`, `enable secret …`).
5. `end` back to `#`.
6. `write` (or `copy running-config startup-config`).
7. Only now is it safe to `reload`.

Forgot step 6? You configured a ghost. The next boot is last week’s box.

## Summary

| Idea | Meaning |
| --- | --- |
| Shell | Face of the OS: GUI or CLI |
| Console port | Local CLI only; not a data NIC |
| Rollover | 1↔8, 2↔7, … into the RJ45 console |
| User EXEC `>` | Look, a little; no config, no reload |
| Privileged EXEC `#` | Full `show`, reload, save; still no config edits |
| Global config `(config)#` | Edits running-config now |
| `do` | Run an EXEC command without leaving config |
| running-config | RAM, live, lost on reload |
| startup-config | NVRAM, loaded at boot |
| `write` / `copy run start` | RAM → NVRAM |
| `enable password` | Legacy, cleartext (type 7 if you ask) |
| `enable secret` | Hash; wins if both are set |
