## 1. Executable JAR

Boot’s default path: package a **fat JAR** and run with embedded Tomcat (or another embedded server).

Requirements:

1. `<packaging>jar</packaging>` (or omit — jar is default)
2. `spring-boot-maven-plugin` so the **repackage** goal runs on `mvn package`

```xml
<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId> <!-- repackages fat JAR -->
</plugin>
```

```bash
mvn package
java -jar target/course-tracker-app-jar-1.0.0.jar
```

Inside the fat JAR:

- `Main-Class` → Boot loader (`JarLauncher`)
- `Start-Class` → your `@SpringBootApplication`
- App classes under `BOOT-INF/classes/`, deps under `BOOT-INF/lib/`
- `layers.idx` for Docker-friendly layering: `dependencies`, `spring-boot-loader`, `snapshot-dependencies`, `application`

Inspect layers:

```bash
java -Djarmode=layertools -jar app.jar list
java -Djarmode=layertools -jar app.jar extract --destination layers
```

```xml
<build>
  <plugins>
    <!-- spring-boot-maven-plugin here -->
  </plugins>
</build>
```

## 2. WAR on an application server

When ops already runs WildFly / Tomcat / JBoss:

1. `<packaging>war</packaging>`
2. Mark embedded Tomcat `provided` if the server supplies the servlet container
3. Extend `SpringBootServletInitializer` and point at your main class

```java
public class ServletInitializer extends SpringBootServletInitializer {
  @Override
  protected SpringApplicationBuilder configure(SpringApplicationBuilder application) {
    return application.sources(CourseTrackerSpringBootApplication.class); // WAR entry
  }
}
```

WildFly extras (book demo): exclude conflicting `logback-classic`; set context root via `jboss-web.xml`. Automate with `wildfly-maven-plugin` (`deploy` on install, `undeploy` on clean) and keep credentials out of the POM (e.g. `settings.xml`).

```java
import org.springframework.boot.builder.SpringApplicationBuilder;
import org.springframework.boot.web.servlet.support.SpringBootServletInitializer;

public class ServletInitializer extends SpringBootServletInitializer {

  @Override
  protected SpringApplicationBuilder configure(SpringApplicationBuilder application) {
    return null;
  }
}
```

## 3. Cloud Foundry (PaaS)

**PaaS** manages runtime/OS; you manage app + data. Cloud Foundry can take a JAR (or source) and a **buildpack**.

Typical flow:

```bash
cf login -a <API_ENDPOINT> -u <USER>
mvn clean install
cf push   # reads manifest.yml
cf apps   # show routes
```

```yaml
applications:
  - name: course-tracker-app-cf
    instances: 1
    memory: 1024M
    path: target/course-tracker-app-cf-1.0.0.jar # artifact to push
    random-route: true
    buildpacks:
      - java_buildpack
```

Bind managed services (`cf create-service`, `cf bind-service`). VCAP / `java-cfenv` expose credentials into Spring `Environment`.

```yaml
applications:
  - name: course-tracker-app-cf
    instances: 1
    memory: 1024M
    # path + buildpacks
```

## 4. Heroku

Heroku builds from **Git** (or Maven plugin), runs on **dynos**, and can attach add-ons (e.g. Postgres).

```bash
heroku login
git init && git add . && git commit -am "first"
heroku create
heroku addons:create heroku-postgresql
git push heroku master   # or main, per app default
heroku open
heroku logs
```

Spring often reads `SPRING_DATASOURCE_URL` / username / password injected by the Postgres add-on. Prefer secrets in config vars, not committed files.

## 5. Docker

A **image** packages app + runtime; a **container** is a running instance. Same image → more consistent Dev/UAT/Prod.

### Simple Dockerfile

```dockerfile
FROM adoptopenjdk:11-jre-hotspot
ADD target/*.jar application.jar
ENTRYPOINT ["java", "-jar", "application.jar"]
EXPOSE 8080
```

```bash
docker build --tag course-tracker:v1 .
docker run -p 8080:8080 course-tracker:v1
```

### Layered multi-stage (better cache)

Extract Boot layers, then `COPY` each layer separately; entrypoint `JarLauncher`.

### Boot buildpacks (no hand-written Dockerfile)

```bash
mvn spring-boot:build-image -Dspring-boot.build-image.imageName=course-tracker:v3
```

Uses Cloud Native / Paketo buildpacks — similar idea to CF/Heroku: source/JAR → runnable image.

```dockerfile
FROM adoptopenjdk:11-jre-hotspot
# ADD jar, ENTRYPOINT, EXPOSE
```

## 6. Kubernetes

Kubernetes **orchestrates** containers across a cluster (Pods, Deployments, Services). Local demos often use Kind / Minikube / Docker Desktop.

Typical path:

1. Build/tag image (`course-tracker:v3` → `musibs/course-tracker`)
2. Push to a registry (needed for remote nodes)
3. Create Deployment + Service YAML
4. `kubectl apply -f .`
5. Port-forward for local access if using ClusterIP

```bash
kubectl create deployment course-tracker --image musibs/course-tracker --dry-run=client -o=yaml > deployment.yaml
kubectl create service clusterip course-tracker-service --tcp 80:8080 -o yaml --dry-run=client > service.yaml
kubectl apply -f .
kubectl port-forward pod/<pod-name> 8080:8080
```

Deployment snippet idea: `kind: Deployment`, container `image: musibs/course-tracker`, `replicas: 1`.  
Service: map port **80** → container **8080** (`ClusterIP`).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: course-tracker
spec:
  replicas: 1
  selector:
    matchLabels:
      app: course-tracker
  template:
    metadata:
      labels:
        app: course-tracker
    spec:
      containers:
        - name: course-tracker
          image: musibs/course-tracker # image from registry
```

## 7. RedHat OpenShift

OpenShift is enterprise Kubernetes with a developer console and extra workflows (From Git, Dockerfile, container image, …).

Sandbox-style flow:

1. Create/login to OpenShift Developer Sandbox  
2. **From Git** → paste repo URL  
3. Platform builds, deploys to a Pod, exposes a **Route**  
4. Use liveness / readiness / startup probes for health  

Same container ideas as K8s; OpenShift adds opinionated tooling and multi-tenant ops.

## Choosing a strategy

| Approach | When it fits |
|---|---|
| Fat JAR | Simple VMs, CI artifact, embedded server |
| WAR | Existing app-server estate |
| CF / Heroku | PaaS, less infra ownership |
| Docker | Portable runtime unit |
| Kubernetes / OpenShift | Scale, self-heal, multi-service |

Always match **availability, compliance, and team skill** — not hype.
